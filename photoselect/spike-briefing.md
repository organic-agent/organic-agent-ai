# AI 셀렉 — 지금 뭘 하고 있나 (멘토 미팅용 정리)

> 한 줄 요약: **"어떤 AI 모델을 쓸지 결정하기 위한 사전 실험(스파이크) 단계"**입니다.
> 본 기능을 만들기 전에, 후보 모델들이 우리 웨딩 사진에서 실제로 쓸 만한지·빠른지·상업적으로
> 써도 되는지를 실측하고 있고, 이게 끝나야 본 구현에 들어갑니다.

---

## 1. 만들려는 기능이 뭔가 (30초 버전)

부부가 웨딩 갤러리(수천 장)에서 앨범에 넣을 사진을 고르는 "셀렉" 과정을 AI가 돕는 기능.

- **기능 A. 추천 채우기** — "목표 50장 중 12장만 골랐으면, 나머지 38장을 이유와 함께 추천"
- **기능 B. 사진 진단** — "이 사진 괜찮아?"라고 물으면 근거 있는 답을 줌

핵심 원칙 두 가지:

1. **AI는 제안만, 결정은 사람이.** 점수 낮다고 사진을 걸러내지 않음(작가가 의도한 흔들림·아웃포커스 컷 보호). 제출 버튼은 AI가 못 누름.
2. **원가 원칙.** 수천 장 전수 처리는 경량 모델(CPU)로, 비싼 LLM(Claude)은 사용자 요청 1건당 소규모 호출만.

## 2. 어떻게 동작하게 설계했나 — "점수 파이프라인"

두 기능 다 같은 전처리 위에서 돕니다. 갤러리가 올라오면 **사진마다 딱 한 번** 아래 신호를 계산해서 DB에 저장해 두고, 나중에 사용자가 요청하면 저장된 신호를 읽어 조립만 합니다.

| 단계 | 질문 | 모델 (1순위 후보) | 산출 |
|---|---|---|---|
| ① 기술 품질 | 초점·흔들림·노출·노이즈가 정상인가? | **ARNIQA** (WACV 2024, ResNet-50) | `technical_score` |
| ② 미학 | 구도·조명·색이 잘 찍혔나? | **LAION Aesthetic v2** (CLIP ViT-L/14 + MLP) | `aesthetic_score` |
| ③ 얼굴 신호 | 눈 떴나? 웃었나? 얼굴 몇 명? | **MediaPipe Face Landmarker** | `eyes_open`, `smile`, 얼굴 수·크기 |
| ④ 장면 태그 | 본식/야외/스튜디오, 클로즈업/단체? | CLIP 제로샷 (②의 임베딩 재사용 → 추가 비용 ~0) | `scene_tags` |
| ⑤ 중복 묶기 | 거의 같은 연사 컷끼리 묶기 | 기존 embedder 임베딩 클러스터링 (모델 없음) | `cluster_id` |
| ⑥ 묶음 내 순위 | 연사 5장 중 베스트는? | ③ 신호의 규칙 합성 (전원 눈 뜸 > 미소 > 선명도) | `cluster_rank` + 이유 코드 |

왜 이 구조인가 (미팅에서 물어볼 만한 것):

- **왜 절대 점수만으로 안 고르나?** 학계(Photo Triage, SIGGRAPH 2016)와 프로덕션(Google Top Shot)이 공통으로 보여준 사실 — 연사처럼 거의 같은 사진들은 미학 점수가 다 비슷하게 나와서 "그 중 뭐가 제일 나은지"는 눈 뜸·표정 같은 **얼굴 단위 신호로 상대 비교**해야 갈린다. 그래서 ③⑥이 따로 있다.
- **왜 점수를 "갤러리 내 상위 몇 %"로만 쓰나?** 공개 모델은 일반 사진(AVA 등)으로 학습돼서 웨딩 사진의 절대 점수는 못 믿는다. 같은 작가·같은 갤러리 안에서의 상대 비교는 안전하다.
- **LLM은 어디에?** 위 표에는 없다. 전수 처리 단계엔 LLM 호출 0회. 기능 A에서 "38장의 선정 근거(구조화 데이터)를 부부에게 보여줄 한 줄 문장으로" 바꿀 때 갤러리당 1회, 기능 B에서 요청당 1회만 Claude(Bedrock)를 부른다. LLM은 **선택을 바꾸지 못하고 문장만 만든다** (photo_id 검증 가드레일).

## 3. 그래서 스파이크에서 뭘 하고 있나

설계는 끝났지만, 위 표의 모델들은 전부 "논문·공개 모델 조사로 고른 **가설**"입니다. 실제 우리 데이터에서 검증 안 된 것이 세 가지라 본 구현 전에 확인합니다.

| 확인할 것 | 왜 중요한가 | 어떻게 재나 |
|---|---|---|
| **(a) 도메인 갭** — 공개 모델 점수가 작가의 실제 셀렉과 상관이 있나? | 최대 리스크. 상관이 없으면 ①② 가중치를 낮추고 얼굴 신호(③) 중심으로 축을 옮겨야 함 | 골든셋(작가 최종 셀렉 라벨) 대비 **AUC, recall@K** |
| **(b) 속도** — 3,000장을 AWS Lambda 15분 제한 안에 처리 가능한가? | 배치 실행 모양(Lambda)이 성립하는지 결정. 안 되면 병렬화 → ONNX → Fargate 순으로 대응 | 러너별 **사진당 처리 시간(초)** 실측 |
| **(c) Bedrock 리전** — 서울(ap-northeast-2)에서 쓰려는 Claude 모델이 제공되나? | 미제공이면 크로스 리전 프로필로 우회해야 하고, 사진을 보내는 기능 B는 데이터 위치 정책 이슈 | `bedrock_check.py`로 모델·프로필 목록 조회 |

추가로 모델 선정 기준에 **라이선스**가 있습니다 — 이건 조사 단계에서 이미 1차 스크리닝을 끝냈습니다(아래 §6).

### 스파이크 하네스 (`photoselect/scripts/spike/`)

서비스 코드가 아니라 **버릴 수 있는 로컬 실험 스크립트**입니다. 구성:

```
manifest.py      ../dataset 스캔 → 사진 목록 CSV (photo_id, path, group, selected)
run.py           러너별로 점수 + 처리 시간 계산 → scores.csv (중단 후 재실행 시 이어서)
runners/         mediapipe_faces / arniqa / laion_aesthetic  (모델별 어댑터)
metrics.py       AUC · recall@K · 러너 간 순위 상관(SRCC)
report.py        지표 요약 + 속도 표 → report.md
bedrock_check.py 서울 리전 Bedrock 가용성 조회
weights/         고정 버전 가중치 (.task / .pth)
```

평가 데이터(`../dataset`, 8,133장):

- `dataset1` — 실제 고객 스냅 6개 폴더(HEIC, 944장)
- `dataset2` — 웨딩 촬영본 JPG 7,189장

평가 지표를 SRCC(점수 상관)가 아니라 **AUC·recall@K**로 잡은 이유: 우리 정답 라벨은 "작가가 최종 셀렉했나"의 **이진 라벨**이라, "점수가 선택/미선택을 얼마나 가르는가(AUC)"와 "점수 상위 K장 중 작가 셀렉이 몇 장 포함되나(recall@K, K = 실제 셀렉 장수)"가 기능 목표(추천 채우기)에 직접 대응하는 지표입니다.

## 4. 지금까지 나온 결과 (근거)

### ✅ (c) Bedrock 서울 리전 — 확정 (2026-08-20)

- 쓰려던 **Claude Opus 5·Haiku 4.5는 서울 리전 온디맨드 미제공.** `apac.` 크로스 리전 프로필에도 없음.
- **`global.` 크로스 리전 프로필로는 호출 가능** (ACTIVE 확인): `global.anthropic.claude-opus-5`, `global.anthropic.claude-haiku-4-5-20251001-v1:0` → 기술 스택 문서에 반영 완료.
- 온디맨드로 되는 건 claude-3.5-sonnet(2024-06)·claude-3-haiku 등 구세대뿐.
- **따라오는 이슈**: `global.`은 요청이 해외 리전으로 라우팅될 수 있음. 기능 A(텍스트 신호만 전송)는 문제 없고, 기능 B(미리보기 이미지 1장 전송)는 데이터 위치 정책 검토 필요.

### ✅ (b) 속도 — 1차 스모크 실측 (M4 Pro CPU, dataset2 10장, 미리보기 1600px 가정)

| 러너 | 단계 | 평균 s/장 | 3,000장 직렬 환산 |
|---|---|---|---|
| MediaPipe faces | ③ | 0.127 | 6.4분 |
| LAION aesthetic v2 | ② | 0.199 | 9.9분 |
| ARNIQA | ① | 0.369 | 18.4분 |
| **합계** | | **~0.70** | **~35분** |

결론과 해석:

- **직렬로 돌리면 Lambda 15분 예산을 확실히 초과** → 프로세스 풀 병렬화가 전제 조건. 설계 단계의 예상(~0.8s/장)과 거의 일치.
- 단, M4 Pro는 Lambda 코어보다 빠르므로 **Lambda 10GB(≈6 vCPU) 환경에서 재실측 필요**. 초과 시 대응 순서는 정해 둠: 병렬화·해상도 조정 → ONNX Runtime → 갤러리 분할 자기 재호출(멱등 설계라 재호출 = 재개) → ECS Fargate(최후).
- 점수 자체는 정상 범위로 나옴: ARNIQA 0.49~0.52, LAION 5.9~6.1(AVA 1~10 축). 10장이라 분산이 작은 건 당연 — 전수 실행에서 갤러리 내 백분위가 변별력이 있는지가 본 게임.

### ⏳ (a) 도메인 갭 — 아직 미측정 (가장 중요한데 아직 못 한 것)

- **막힌 이유: 골든셋 라벨이 없다.** "작가가 이 사진을 최종 셀렉했는가"를 manifest의 `selected` 열에 채워야 AUC·recall@K를 낼 수 있는데, 라벨 소스(작가 실제 셀렉 결과) 확보가 선결.
- 하네스·지표 코드는 준비 완료 — 라벨만 들어오면 `run.py` 전수 실행 → `report.py`로 바로 나옴.
- 멘토님께 여쭤볼 포인트: **라벨 확보 경로**(작가 셀렉 결과를 받을 수 있는지 / 없으면 내부에서 라벨링할지).

### 🔍 관찰 — 검증 필요

- **작은 얼굴에서 눈 뜸 신호가 불안정할 수 있음.** 2인 전신 컷(얼굴이 프레임의 ~3.6%)에서 `eyes_open` 최소값이 0.2대로 낮게 나옴. 실제로 눈을 감은 건지, MediaPipe blendshape가 작은 얼굴에서 흔들리는 건지 확인 필요. 후자면 "얼굴 크롭 후 재검출"로 바꿔야 하는데 처리 비용이 올라감.

## 6. 예상 질문과 답

**Q. 왜 바로 만들지 않고 스파이크부터?**
모델 채택이 틀리면 파이프라인·DB 스키마(`photo_analysis`)·Lambda 사이징을 전부 다시 해야 해서. 조사 단계에서 가장 큰 리스크로 꼽은 게 "공개 모델이 웨딩 사진에서 안 먹힐 가능성"이고, 이건 실측 말고는 알 방법이 없음.

**Q. 모델은 어떻게 골랐나?**
논문·벤치마크 조사(`docs/research.md`)로 1차 스크리닝. 기준은 (a) 골든셋 상관 (b) **라이선스** (c) CPU 속도·크기 (d) 유지보수성 (e) 특허. 실제로는 정확도보다 **라이선스가 진짜 제약**이었음 — 성능 좋은 모델 다수(Q-Align, pyiqa 라이브러리, InsightFace 사전학습 모델, dlib 랜드마크 등)가 비상업 라이선스. 상업적으로 깨끗한 것 중 고른 게 ARNIQA·LAION v2·MediaPipe(전부 Apache-2.0).

**Q. 왜 LLM(Claude)으로 사진을 직접 안 고르나?**
원가. 수천 장에 vision 호출을 하면 갤러리당 비용이 감당 안 됨. 또 LLM이 직접 고르면 근거가 환각일 수 있음. 그래서 경량 모델이 수치 신호 + 이유 코드(`EYES_CLOSED`, `BEST_SMILE`)를 만들고, LLM은 그걸 문장으로만 바꿈.

**Q. 개인화는?**
부부가 직접 고른 사진(12장)의 임베딩 유사도가 유일한 개인화 신호. 평점(`photo_ratings`)은 정책상 AI 입력에서 제외. 문헌상 개인화 미학(PIAA)은 신호가 약해서(SRCC 0.44~0.58) 보조 신호로만 쓰고 하드 필터 금지 — 설계와 일치.

**Q. 실패하면?**
①② 상관이 낮으면 얼굴 신호(③)·클러스터 순위(⑥)·커버리지 중심으로 축을 옮김. 속도가 안 나오면 Fargate까지 단계적 대응 경로가 있음. 스파이크가 "안 된다"를 빨리 알려주는 것도 성공.
