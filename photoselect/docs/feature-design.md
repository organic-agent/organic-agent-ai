# photoselect 기능 설계 — 추천 채우기 & 사진 진단

`plan.md`(아키텍처·원칙)와 `research.md`(모델 선정 근거)를 전제로, 사용자에게 실제로
제공할 두 기능의 **단계별 처리·산출물·제공 형태**를 명세한다.

- **기능 A. 추천 채우기** — 목표 50장 중 사용자가 12장을 골랐다면, 남은 **38장을 이유와
  함께 추천**해 초안을 완성한다.
- **기능 B. 사진 진단** — 사용자가 고른(또는 고민 중인) 사진이 "사진학적으로 괜찮은지"
  물으면 근거 있는 응답을 준다.

두 기능 모두 같은 **점수 파이프라인(0단계)** 위에서 동작한다. 무거운 ML 추론은 갤러리당
1회로 끝내고, 사용자 요청 시점에는 저장된 신호를 읽어 조립 + LLM 소규모 호출만 한다.

---

## 0단계. 점수 파이프라인 (배치 Lambda, 갤러리 임베딩 완료 후 1회)

사용자가 셀렉을 시작하기 전에 미리 끝내 두는 전처리. 입력은 embedder가 만든 미리보기
JPEG(`photos.preview_key`)와 pgvector 임베딩.

| # | 처리 | 모델 (라이선스) | 의미 | 산출물 (`photo_analysis`) |
|---|---|---|---|---|
| 0-1 | 얼굴 검출 + 랜드마크 + blendshape | **MediaPipe Face Landmarker** (Apache-2.0) | 얼굴 위치·눈 뜸·미소 등 얼굴 단위 원시 신호 | 얼굴별 bbox, `eyes_open`(eyeBlink 역수), `smile`(mouthSmile), 얼굴 수 |
| 0-2 | 기술 품질 점수 | **ARNIQA** (Apache-2.0, ResNet-50+선형회귀) — 전체 프레임 + 얼굴 크롭 재적용 | 초점·흔들림·노출·노이즈가 정상인가 (퍼널 ①) | `technical_score`, `face_sharpness` |
| 0-3 | 미학 점수 | **LAION Aesthetic v2** (Apache-2.0) — CLIP ViT-L/14 임베딩 + MLP. CLIP 임베딩은 0-4·장면 태그와 공유 | 구도·조명·색이 잘 찍혔는가 (퍼널 ②) | `aesthetic_score` (+ 스파이크 결과에 따라 Charm 교체/병행) |
| 0-4 | 장면 태그 | CLIP 제로샷 분류 (0-3과 임베딩 공유 → 추가 원가 ~0) | 본식/야외/스튜디오 × 클로즈업/전신/단체 — 커버리지 축 | `scene_tags` |
| 0-5 | 근접 중복 클러스터링 | pgvector 임베딩 union-find (기존 설계) | "거의 같은 사진 묶음" 식별 (퍼널 ③ 입력) | `cluster_id` |
| 0-6 | 클러스터 내 순위 | 0-1·0-2 신호의 결정적 합성 (예: 전원 눈 뜸 > 미소 > 얼굴 선명도) | 같은 장면 연사 중 베스트 컷은 무엇인가 (퍼널 ③) | `cluster_rank`, `rank_reason_code` (예: `EYES_CLOSED`, `BEST_SMILE`) |

- 모든 점수에 `model_version` 저장 — 모델 교체 시 재적재 대상 식별.
- **점수 해석은 갤러리 내 백분위로 통일한다.** 공개 모델의 절대 점수는 웨딩 도메인에서
  신뢰가 낮지만(research.md — AVA 도메인 갭), 같은 갤러리·같은 작가 사진끼리의 상대 비교는
  안전하다. 이후 모든 단계는 "이 갤러리에서 상위 몇 %"로만 점수를 쓴다.
- `rank_reason_code`가 중요하다: 이 시점에 **근거의 재료를 코드로 남겨야** 뒤에서 LLM이
  환각 없이 문장화할 수 있다.
- LLM 호출 0회. 수천 장 갤러리도 경량 모델 CPU 추론으로 처리 (Lambda 15분 실측은 스파이크).

## 기능 A. 추천 채우기 — "38장을 이유와 함께"

### 트리거와 실행 모양

사용자가 셀렉 화면에서 "나머지 AI로 채우기" 요청 → wes가 실행 조건 검증(갤러리 OPEN,
목표 장수 존재, 활성 잡 없음 등) 후 배치 Lambda EVENT 트리거. 0단계가 끝나 있으므로
이 잡은 **조립 + LLM 1회 호출**뿐이라 수십 초 내 완료된다.

### A-1. 입력 확정

- 목표 장수 50, 수동 선택 12장 (`photo_selection_items` MANUAL — 읽기 전용, 불가침)
- 채울 슬롯 = 50 − 12 = 38. 전체 사진 < 목표면 전부 선택 + `shortfall` 기록.

### A-2. 취향 신호 추출 (개인화)

- **수동 선택 12장이 유일한 개인화 신호다** (`photo_ratings` 접근 금지 정책).
- 12장의 CLIP 임베딩으로 취향 프로파일을 만든다: 단순 센트로이드가 아니라 **장면 태그별
  부분 센트로이드** (야외에서 고른 것, 클로즈업에서 고른 것…). 후보 사진마다
  `preference_score` = 같은 장면군 선택 사진과의 최대 유사도.
- 근거: 예시 기반 재정렬이 특징 기반보다 사용자 선호 2:1 (Yeh & Barsky, ACM TOMM 2014).
- 12장 미만이거나 0장이면(콜드스타트) 이 항의 가중치를 0으로 — 점수 순 정렬로 동작.

### A-3. 커버리지 분석

- 갤러리를 `scene_tags` × `taken_at` 타임라인 구간의 격자로 나누고, 수동 12장이 이미
  커버한 칸과 빈 칸을 계산.
- 의미: "본식 사진만 12장 고르셨네요 — 야외와 단체 사진 구간이 비어 있어요"를 아는 단계.
- 산출: 구간별 필요 슬롯 배분 (결정적 규칙, 예: 빈 구간 우선 + 사진 수 비례).

### A-4. 슬롯 채우기 (그리디 선택)

후보 = 미선택 사진 전체. 슬롯마다 다음 합성 점수 최대인 사진을 뽑는다:

```
score = w_t·technical_pct + w_a·aesthetic_pct + w_p·preference_score
        + coverage_bonus(빈 구간이면 가산)
제약   = 같은 cluster에서 이미 뽑았으면 배제(대표 1장 원칙, cluster_rank 1위 우선)
```

- 가중치 초기값은 골든셋(작가 최종 셀렉과의 recall@K)으로 튜닝. DPP는 그리디가 부족할 때의
  후속 옵션 (research.md §④ — YouTube CIKM 2018 템플릿).
- **하드 필터 없음**: technical 점수가 낮아도 취향·커버리지로 뽑힐 수 있고, 안 뽑힌 사진도
  제거되지 않는다.
- 산출: 38장 + 사진별 **선정 근거 구조체** (어떤 항이 결정적이었나, 어느 커버리지 칸을
  채웠나, 클러스터 대안 몇 장, rank_reason_code). 전 과정 결정적(비-LLM)이라 재실행 멱등.

### A-5. LLM 근거 문장화 (Bedrock Claude, 잡당 1회)

- 입력: 38장의 선정 근거 구조체 (JSON — **이미지 없음**, 텍스트 신호만).
- 프롬프트: "각 사진의 신호를 부부에게 보여줄 한 줄 추천 이유로 써라. 점수 숫자 언급 금지,
  단정 대신 제안 톤, 신호에 없는 내용 금지." + structured outputs로 `{photo_id, reason}` 배열.
- 예: `BEST_SMILE` + 야외 구간 커버 → "야외 촬영 중 두 분 표정이 가장 자연스러운 컷이에요.
  비슷한 사진 4장 중에서 골랐어요."
- **가드레일**: 응답의 photo_id가 선정 목록과 다르면 거부, 누락분은 코드 기반 템플릿 문장으로
  폴백. LLM은 선택을 바꿀 수 없고 문장만 만든다.
- 원가: 갤러리당 텍스트 1회 호출 (수천 토큰) — 원가 원칙 부합. vision 호출 없음.

### A-6. 저장과 사용자 제공

- 저장: `photo_selection_items`에 `source='AI'` 38행 + 근거, 잡 상태 전이와 단일 트랜잭션.
- UI 제공 형태 (wes/프론트 계약):
  - 추천 사진은 수동 선택과 **시각적으로 구분** (AI 배지 + 근거 한 줄)
  - 사진마다 "비슷한 컷 N장 보기" — 같은 클러스터의 차순위 컷을 펼쳐 원클릭 교체
  - 커버리지 요약 한 줄: "직접 고르신 12장에 더해, 야외 9장·단체 6장·원판 5장… 을 채웠어요"
  - 추천 제외는 목록에서 빼는 것일 뿐 사진은 그대로 — 언제든 되살리기
  - **확정·제출 버튼은 AI와 무관** — 부부가 눌러야만 진행 (자동 제출 금지)

## 기능 B. 사진 진단 — "이 사진 괜찮아?"

### 실행 모양

사용자가 특정 사진에서 "이 사진 어때?" (버튼 또는 자유 질문) → **저지연 동기 API**
(P2 보정 구조화와 같은 모양). 0단계 신호가 이미 있으므로 **ML 재추론 없이 DB 조회 +
LLM 1회**로 응답한다. 목표 지연 2~3초.

### B-1. 신호 조회 (DB만)

해당 사진의 `photo_analysis` 행 + 같은 클러스터 형제 컷들 + 갤러리 백분위:

- 기술: "이 갤러리에서 선명도 상위 8%" / "야간 컷 치고 노이즈 평균 수준"
- 얼굴: 눈 뜸·미소 값, 몇 명 중 몇 명이 카메라를 보는지
- 클러스터: "거의 같은 컷이 5장 있고 이 사진이 2위 — 1위는 신부님 눈이 더 또렷"
- 취향: 사용자가 이미 고른 사진들과의 유사도 ("고르신 사진들과 분위기가 비슷해요")

### B-2. LLM 응답 생성

- 입력: 위 신호 구조체 + 사용자 질문 텍스트 + **해당 사진 미리보기 1장** (vision — 요청
  단위 1장이라 원가 원칙 내. 신호가 충분하면 vision 생략 가능하게 플래그).
- 톤 규칙 (프롬프트 강제):
  - **판정하지 않는다** — "별로예요" 금지. 신호를 알려주고 판단은 사용자에게
  - 작가 의도 존중 — 의도적 아웃포커스·역광일 수 있음을 전제로 표현
  - 대안이 있으면 제시하되 강요하지 않음: "같은 순간의 다른 컷도 한 번 보시겠어요?"
- 예시 응답: "기술적으로 아주 좋은 컷이에요 — 이 갤러리에서 선명도 상위 10% 안에 들고
  두 분 다 눈을 뜨고 계세요. 거의 같은 장면이 4장 더 있는데, 그중 이 컷의 미소가 가장
  자연스러워요. 다만 배경 노출이 살짝 밝은 편인데, 이런 톤을 좋아하시면 그대로 좋아요."
- structured output으로 `{verdict_signals[], comparison, suggestion?}`를 함께 받아 UI가
  배지(눈 뜸 ✓, 선명도 상위 10% 등)로도 렌더링할 수 있게 한다.

## DB·API 계약 요약 (스키마는 wes Flyway 소유)

| 대상 | 내용 |
|---|---|
| `photo_analysis` (신규) | 0단계 산출물 전부 + `model_version` |
| `ai_selection_jobs` (신규) | 기능 A 잡 상태 (갤러리당 활성 1개) |
| `photo_selection_items` | `source`, `ai_reason` 컬럼 — AI 행만 쓰기 |
| 동기 API (기능 B) | `POST /diagnose {photoId, question?}` → 신호+문장 응답. wes 경유 인증 |

## 원가 프로파일 (갤러리 3,000장 가정)

| 단계 | 호출 | 비고 |
|---|---|---|
| 0단계 경량 모델 | 사진당 CPU 추론 × 4종 | LLM 0회. 시간 실측이 스파이크 대상 |
| 기능 A | 갤러리당 LLM 텍스트 1회 | 이미지 미포함, structured output |
| 기능 B | 요청당 LLM 1회 (이미지 ≤1장) | 사용자 대기 — 저지연 모델 프로파일 |

## 구현 순서 (plan.md §6의 구체화)

1. 0단계 파이프라인 스캐폴드 + `../dataset` 골든셋 end-to-end (스파이크 겸용)
2. `photo_analysis` 마이그레이션 협의(wes) → 0단계 배치 Lambda 배포
3. 기능 A: A-1~A-4 (LLM 없이 템플릿 근거로 먼저) → 골든셋 recall@K 측정
4. A-5 LLM 근거 붙이기 → 내부 검수 (근거 문장이 신호와 어긋나는지 샘플 점검)
5. 기능 B 동기 API (A와 신호 공유라 증분 작업 적음)
6. 프론트 계약 (배지·교체 UI·커버리지 요약) — wes/organic-agent-test-web 트랙과 협의
