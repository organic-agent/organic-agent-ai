# AI 셀렉터 스키마 제안 — 최종 엔티티

작성 2026-08-25 · 상태: **제안. wes 코드는 아직 안 바꾼다.** AI 셀렉 기능이 완성되면 일괄 적용.

근거: `plan.md` §5(DB 계약), `photoselect/store.py`(코드 쪽 실물), wes `.claude/rules/migration.md`.
wes의 현재 스키마는 V9까지이고 여기 적힌 테이블은 **전부 신규**다.

---

## 0. 나누는 기준

wes가 이미 세운 원칙이 있다 (`PhotoRating.kt`, `V8__photo_ratings.sql` 주석):

> 사람이 사진에 남기는 것은 계속 늘어난다 — photos가 넓어지면 목록 조회가 쓰지도 않는 컬럼을 읽는다.

여기에 생명주기 기준을 하나 더한다:

| 부류 | 언제 바뀌나 | 어디에 |
|---|---|---|
| **정체성** (storage_key, 파일명, EXIF) | 업로드 시 한 번. 불변 | `photos` (현행 유지) |
| **모델 파생값** (임베딩, 태그, 점수, 클러스터) | `model_version` 단위로 **통째 재적재** | `photo_analysis` (신규) |
| **사람이 남긴 것** (별점, 담기, 쌍 비교, 추천 반응) | 사용자 행동마다 | 각각 별도 테이블 |
| **잡 상태** | 실행마다 | `ai_*_jobs` |

**`photos.embedding`은 현재 정체성 테이블에 있지만 모델 파생값이다.** `Photo.applyEmbedding`이
`status`까지 바꾸고, `copyOf`가 벡터를 복사해 들고, 차원 하나가 엔티티·마이그레이션·인프라 세 곳에
묶여 있는 것이 그 결합의 증거다. 최종안에서는 `photo_analysis`로 옮긴다 (§1 참조).

## 1. `photo_analysis` — 모델 파생값 (photos 1:1)

A 배치(갤러리당 1회)가 채우고, 모델이 바뀌면 갤러리 단위로 다시 쓴다. AI 전용 DB 사용자만 쓴다.

```sql
-- 사진 한 장에 대한 모델 파생값 전부. 갤러리당 1회 도는 전수 분석(A)이 채운다.
--
-- photos에 붙이지 않은 이유 둘. ① 13컬럼(캡션 텍스트·jsonb 포함)이라 목록 조회가 안 쓰는
-- 열을 읽게 된다(photo_ratings와 같은 이유). ② 모델을 바꾸면 갤러리 전체를 통째로 다시
-- 적재한다 -- 정체성 행을 매번 UPDATE하는 것보다 ON CONFLICT DO UPDATE가 맞다.
--
-- 임베딩도 여기 둔다. photos.embedding은 같은 Lambda가 채운다는 이유로 EXIF와 같은 자리에
-- 들어갔지만, EXIF는 불변이고 임베딩은 모델을 바꿀 때마다 바뀐다. 클러스터링·MMR은 임베딩과
-- 태그를 항상 함께 읽으므로 한 테이블이 맞다.
CREATE TABLE photo_analysis
(
    photo_id         BIGINT PRIMARY KEY,
    -- 고정 축 태그 5개. 어휘 계약은 AI repo의 photoselect/axes.py + model_version이 진다.
    -- CHECK/enum을 걸지 않는 이유: 어휘가 바뀔 때마다 마이그레이션이 필요해지고, 어차피
    -- 구버전 행은 model_version으로 판별해 재적재한다.
    scene            VARCHAR(20)  NOT NULL,
    framing          VARCHAR(20)  NOT NULL,
    lighting         VARCHAR(20)  NOT NULL,
    expression       VARCHAR(20)  NOT NULL,
    subjects         VARCHAR(20)  NOT NULL,
    -- VLM 캡션 1문장. 이유 문장의 소재. 없을 수 있다(VLM 미실행).
    caption          TEXT,
    -- 갤러리 내 백분위 0~100. 원점수가 아니다 -- 모델마다 단위가 달라 갤러리 안 순위로 통일한다.
    technical_pct    REAL         NOT NULL,
    aesthetic_pct    REAL         NOT NULL,
    -- {face_count, max_face_ratio}. 얼굴 신호는 클러스터 대표 선정에만 쓴다.
    face_boxes       JSONB        NOT NULL DEFAULT '{}',
    -- 원점수 {technical_score, aesthetic_score, eyes_open, smile}. 모델이 바뀌면 키가 바뀐다.
    sub_scores       JSONB        NOT NULL DEFAULT '{}',
    -- 근접 중복(연사) 클러스터. 갤러리 안에서만 유일한 번호.
    cluster_id       INTEGER      NOT NULL,
    -- 클러스터 안 순위. 0이 대표. rank_reason_code는 대표가 된 이유(eyes_open/technical/aesthetic/single/tie).
    cluster_rank     INTEGER      NOT NULL,
    rank_reason_code VARCHAR(20),
    -- 임베딩. photos.embedding에서 옮겨 온다. 차원은 AI repo config와 함께 관리.
    embedding        vector(768),
    -- 이 행을 만든 파이프라인 버전. 다르면 재적재 대상.
    model_version    VARCHAR(40)  NOT NULL,
    created_at       TIMESTAMP(6) WITH TIME ZONE,
    updated_at       TIMESTAMP(6) WITH TIME ZONE,
    CONSTRAINT fk_photo_analysis_photo FOREIGN KEY (photo_id) REFERENCES photos (id) ON DELETE CASCADE
);
-- 갤러리 단위 조회는 photos.gallery_id로 조인한다. 여기에 gallery_id를 중복 저장하지 않는다.
```

**쓰기 규약**: `INSERT … ON CONFLICT (photo_id) DO UPDATE SET …` — 재실행 멱등.
**읽기 규약**: B는 `photos.gallery_id = ? AND photos.deleted_at IS NULL`로 조인해서 읽는다
(`@SQLRestriction`은 JPA 경로만 지키므로 네이티브 SQL에서 직접 건다 — wes 규칙).

**`photos`에서 빠지는 것** (일괄 적용 시): `embedding` 컬럼, `Photo.EMBEDDING_DIMENSION`,
`applyEmbedding`의 벡터 부분, `copyOf`의 벡터 복사. `PhotoStatus.EMBEDDED`는 "분석 완료"의 뜻이 된다.

## 2. `ai_analysis_jobs` — A 잡 큐

```sql
-- 갤러리 전수 분석 잡. DB가 곧 큐다(별도 큐 서비스 없음).
-- wes가 업로드 완료 시 PENDING으로 넣고 EC2를 깨운다. EC2 루프가 RUNNING → DONE/FAILED로 옮긴다.
CREATE TABLE ai_analysis_jobs
(
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    gallery_id    BIGINT       NOT NULL,
    -- PENDING / RUNNING / DONE / FAILED
    status        VARCHAR(20)  NOT NULL,
    -- RUNNING이 20분을 넘기면 wes가 PENDING으로 되돌린다(EC2가 죽은 경우).
    started_at    TIMESTAMP(6) WITH TIME ZONE,
    finished_at   TIMESTAMP(6) WITH TIME ZONE,
    error         TEXT,
    -- 처리 결과 요약 {targets, processed, failed, clusters, elapsedSeconds, …}
    result        JSONB,
    created_at    TIMESTAMP(6) WITH TIME ZONE,
    updated_at    TIMESTAMP(6) WITH TIME ZONE,
    CONSTRAINT fk_ai_analysis_jobs_gallery FOREIGN KEY (gallery_id) REFERENCES galleries (id) ON DELETE CASCADE
);
-- 갤러리당 살아 있는 잡은 하나. 부분 유니크라 DONE/FAILED 이력은 쌓인다.
CREATE UNIQUE INDEX uk_ai_analysis_jobs_active
    ON ai_analysis_jobs (gallery_id) WHERE status IN ('PENDING', 'RUNNING');
```

## 3. `ai_recommendations` — 초안·재추천 (B 산출물 + 고객 반응)

`PhotoSelection`이 갤러리당 하나이므로 `selection_id`가 곧 갤러리 범위다.

```sql
-- AI가 제시한 사진 한 장. 라운드마다 쌓이고, 고객 반응(담기·거절·되돌림)을 같은 행에 기록한다.
-- 한 셀렉에서 한 사진은 한 번만 제시한다(2026-08-25 실측: 다시 보여주면 "아까 본 거잖아").
CREATE TABLE ai_recommendations
(
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    selection_id     BIGINT       NOT NULL,
    photo_id         BIGINT       NOT NULL,
    round            INTEGER      NOT NULL,
    rank             INTEGER      NOT NULL,
    -- {score, prior_z, pref_z, lambda, technical_pct, aesthetic_pct, scene, cluster_id, rank_reason_code}
    -- 점수식이 바뀌어도 스키마가 안 바뀌게 jsonb.
    score_breakdown  JSONB        NOT NULL,
    -- 템플릿 또는 LLM 이유 문장.
    reason           TEXT,
    -- 고객 반응. AI는 쓰지 않고 wes API가 채운다. 지표(수락률·후회율)의 재료.
    presented_at     TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    accepted_at      TIMESTAMP(6) WITH TIME ZONE,
    rejected_at      TIMESTAMP(6) WITH TIME ZONE,
    -- 담았다가 뺀 시각. "전체 수락" 부풀림을 잡는 후회율의 재료.
    unselected_at    TIMESTAMP(6) WITH TIME ZONE,
    -- 'single' | 'bulk'. bulk는 "전체 담기" 버튼.
    accept_mode      VARCHAR(10),
    created_at       TIMESTAMP(6) WITH TIME ZONE,
    updated_at       TIMESTAMP(6) WITH TIME ZONE,
    CONSTRAINT fk_ai_recommendations_selection FOREIGN KEY (selection_id) REFERENCES photo_selections (id) ON DELETE CASCADE,
    CONSTRAINT fk_ai_recommendations_photo FOREIGN KEY (photo_id) REFERENCES photos (id) ON DELETE CASCADE,
    CONSTRAINT uk_ai_recommendations_selection_photo UNIQUE (selection_id, photo_id)
);
CREATE INDEX idx_ai_recommendations_selection_round ON ai_recommendations (selection_id, round);
```

**이 테이블이 `photo_selection_items`를 대체하지 않는다.** 담기는 wes API가 `photo_selection_items`에
쓰고, 같은 시각을 여기 `accepted_at`에도 남긴다. AI는 items를 읽기만 한다.

## 4. `pair_comparison_events` — 온보딩 쌍 비교 (사람이 남긴 것)

```sql
-- "둘 다 괜찮은데 어느 스타일이 좋으세요" 한 번의 답. 첫 라운드 전 8~12개.
-- 같은 scene · 한 축만 다름 · 품질 근접 · 다른 클러스터 -- 쌍 생성 규칙은 AI가, 답은 고객이.
CREATE TABLE pair_comparison_events
(
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    selection_id    BIGINT       NOT NULL,
    photo_a         BIGINT       NOT NULL,
    photo_b         BIGINT       NOT NULL,
    -- photo_a 또는 photo_b. 건너뛰면 행을 만들지 않는다.
    chosen_photo_id BIGINT       NOT NULL,
    -- 두 사진이 갈린 축(framing/lighting/expression/subjects). scene은 규칙상 항상 같다.
    axis            VARCHAR(20)  NOT NULL,
    answered_by     BIGINT       NOT NULL,
    created_at      TIMESTAMP(6) WITH TIME ZONE,
    CONSTRAINT fk_pair_comparison_events_selection FOREIGN KEY (selection_id) REFERENCES photo_selections (id) ON DELETE CASCADE,
    CONSTRAINT ck_pair_comparison_events_chosen CHECK (chosen_photo_id IN (photo_a, photo_b))
);
CREATE INDEX idx_pair_comparison_events_selection ON pair_comparison_events (selection_id);
```

## 5. `ai_selection_jobs` — B 잡 상태

```sql
-- 초안(draft)·재계산(refine) 잡. Lambda EVENT 호출의 추적용. 셀렉당 살아 있는 잡 하나.
CREATE TABLE ai_selection_jobs
(
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    selection_id  BIGINT       NOT NULL,
    -- 'draft' | 'refine'
    mode          VARCHAR(10)  NOT NULL,
    round         INTEGER,
    status        VARCHAR(20)  NOT NULL,
    started_at    TIMESTAMP(6) WITH TIME ZONE,
    finished_at   TIMESTAMP(6) WITH TIME ZONE,
    error         TEXT,
    -- {k, selected, target, lambda, axisConfidence, preferences, …}
    result        JSONB,
    created_at    TIMESTAMP(6) WITH TIME ZONE,
    updated_at    TIMESTAMP(6) WITH TIME ZONE,
    CONSTRAINT fk_ai_selection_jobs_selection FOREIGN KEY (selection_id) REFERENCES photo_selections (id) ON DELETE CASCADE
);
CREATE UNIQUE INDEX uk_ai_selection_jobs_active
    ON ai_selection_jobs (selection_id) WHERE status IN ('PENDING', 'RUNNING');
```

(협의 포인트: §2와 합쳐 `ai_jobs(kind, gallery_id, selection_id, …)` 하나로 갈 수도 있다.)

## 6. 기존 테이블 — 바꾸지 않고 읽기만

| 테이블 | AI가 하는 것 | 근거 |
|---|---|---|
| `photos` | `gallery_id`·`preview_key`·`deleted_at` 읽기 | 미리보기 S3 키, 휴지통 제외 |
| `galleries` | `max_selectable_photo_count` 읽기 | **목표 장수 — 새 컬럼 불필요.** AI repo의 `target_count`가 이 값을 쓴다 |
| `photo_selections` | `id`·`gallery_id`·`status` 읽기 | `status`는 **절대 쓰지 않는다** |
| `photo_selection_items` | `selection_id`별 `photo_id` 읽기 | 담긴 사진 = 후보 제외 + 취향 신호. **쓰지 않는다** |
| `photo_ratings` | `photo_id`·`score`·`rated_by` 읽기 | 사진당 1행(신랑·신부 구분 없음) — AI 모델과 일치. `rated_by`로 작가 별점을 거를지는 협의 |

**`plan.md`의 낡은 문구**: "고객이 담은 것만 wes가 MANUAL로 승격" — `photo_selection_items`에
`source` 컬럼이 없다. AI는 items에 쓰지 않으므로 승격 개념 자체가 없다. "담기는 wes API로만"으로 고친다.

## 9. 미결 — 협의에서 정할 것

1. **`photos.embedding` 이전 시점** — 프로덕션 데이터가 적은 지금이 싸다. 미루면 이전 마이그레이션이 커진다
2. 임베딩 모델 — 현재 embedder는 DINOv2, AI repo 파이프라인은 CLIP을 썼다. **DINOv2로 통일**하고 클러스터 임계값(현재 0.96, CLIP 기준)을 재측정
3. `ai_analysis_jobs` INSERT와 EC2 기동의 책임 — wes가 둘 다 vs wes는 INSERT만
4. `photo_ratings.rated_by`로 작가 별점 제외 여부
5. 잡 테이블 1개(`ai_jobs`) vs 2개
