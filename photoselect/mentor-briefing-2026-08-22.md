# AI 셀렉터 — 설계안 (멘토 보고, 2026-08-22)

지난 미팅(VLM 태깅·개인화·2차 셀렉 제안)과 화이트보드 워크플로우를 반영해 설계를
재정의했습니다. 이 문서는 그 결과와 질문입니다.

## 1. 무엇을 만드는가

> **AI 셀렉터** — 고객(신랑신부)이 사진을 고를 때, 고객이 납득할 추천과 이유를 제시하고,
> 피드백을 받아 다시 제시한다.

- **정답은 없다**는 전제. 작가·고객마다 좋은 사진이 다르고, 실제 "셀렉터"라는 직업은 사진
  지식이 아니라 **설득**으로 고객의 선택을 돕는다. 그래서 "작가 최종 셀렉과 일치율" 같은
  정답 지표는 쓰지 않는다.
- 주인공은 고객. 작가 가치는 간접적(고객이 빨리·만족하며 골라야 납기↓ 클레임↓).
- 범위는 이 기능 하나. 앨범·보정 구조화는 최종점검(11/27) 이후.

## 2. 워크플로우

```
[A] 업로드 직후 · 자체 GPU EC2 온디맨드 · 갤러리당 1회 · 1,000장 10분
    경량 3종(MediaPipe·ARNIQA·LAION) → 오픈 VLM 고정 축 태그 + 캡션 1문장
    → 근접 중복 클러스터 + 대표컷 → photo_analysis

[B] 고객이 "AI 추천" 클릭 · 30초
    별점·선택 충분 → 선호 분포 즉시
    부족         → 온보딩 "둘 중 어느 쪽?" 8~12쌍 (같은 장면·한 축만 다름·품질 근접)
    → score = (1-λ)·사진학 prior + λ·취향 + 장면 커버리지 + MMR
    → 추천 N장 + 이유 (별도 패널, 고객 선택함은 건드리지 않음)

[2차 셀렉] 👍/👎 · 자연어("가족 사진 더") → 축 가중치 조정 → 재추천 · 5초
    고객이 담은 것만 선택함으로 승격
```

### 핵심 설계 결정

| 결정 | 내용 | 이유 |
|---|---|---|
| 사진학이 먼저, 취향은 보정 | λ = f(증거량). 쌍 0개 → ~0.2, 12쌍+별점 20개 → ~0.7. 선호가 50:50인 축은 기여 0 | 쌍 12개는 작은 표본 — 과적합하면 "클로즈업만 100장" |
| 취향 표현 | VLM 태그 선호 분포(장면·구도·조명·표정·인물 5축) + DINOv2 벡터 미세 재정렬 | 분포는 이유 문장을 만들 수 있고, 벡터는 태그로 안 갈리는 미세 취향 |
| 태그 = 고정 enum + 자유 캡션 | 축은 enum 강제, 캡션은 자유 1문장 | 모델 교체(12B↔31B)해도 분포·쌍·이유가 호환 |
| 별점 해금 | `photo_ratings` 읽기 허용, "AI 추천 클릭 = 동의" 고지 | 별점 1~5가 쌍 비교보다 정보량 큼 |
| LLM은 표현·번역만 | 이유 문장 일괄(Bedrock Haiku, 텍스트), 자연어→`{axis, tag, delta}` | 선택은 결정적 코드가. 이미지는 외부로 안 보냄 |
| 경량 3종 유지, 역할 축소 | prior · 클러스터 대표(눈감음 회피) · 쌍의 품질 근접 조건 | 추천 주축은 아님 |

## 3. 인프라

- **VLM 자체 호스팅**: g6.xlarge(L4 24GB, ~$0.8/h)로 시작, 7~12B(Gemma 3 12B / Qwen2.5-VL 7B)
  + vLLM 배치. 31B 필요 시 g6e(L40S 48GB).
- **온디맨드**: wes가 EC2 start → 인스턴스가 DB 잡 큐 소비 → self stop. 기동 4~5분 + 처리
  5~6분 = 10분. 갤러리당 ~$0.5.
- B·C는 Lambda(ML 없음). Bedrock은 서울 온디맨드에 Claude 5 없음 → `global.` 프로필, 텍스트만.
- 비교: Bedrock Haiku로 전수 태깅 시 갤러리당 ~$2 — 비용은 비슷하고, 자체 GPU를 택한 이유는
  **이미지 국내 체류 + 자체 호스팅 경험**.

## 4. 평가 — 정답 없는 문제의 지표

| 지표 | 계산 | 언제 |
|---|---|---|
| **홀드아웃 쌍 예측 정확도** (주) | 12쌍 중 9쌍 학습 → 3쌍 예측. 우연 50% 대비 | **2주 내**, 팀원·지인 5~10명, GPU 불필요 |
| 수락률 @round | 제시 대비 담은 비율, 1차→2차 상승 = 피드백 작동 | 실사용 |
| nDCG | 상위 순위가 더 수락됐는가 (설득력 = 순서) | 실사용 |
| 후회율 | 담았다가 뺀 비율 ("전체 담기" 부풀림 방지) | 실사용 |
| 라운드 수·완료 시간 | 작가 납기 스토리 | 실사용 |

기존 골든셋 라벨(`selected`)·AUC는 폐기. 데이터셋은 태깅·쌍 실험의 사진 소스로만.

## 5. 일정 (14주)

```
W1–2   트랙 B: 100장 로컬 태깅 → 쌍 비교 실험 → 정확도 첫 숫자   ← 설계의 심장, 먼저
W1–3   트랙 A: 12B/7B 처리량 · 31B 품질 비교 · GPU 등급 확정
W1–2   wes V22 (photo_analysis, ai_analysis_jobs)
W3–6   전수 분석 파이프라인(A) — AMI·self stop·1,000장 10분 실측

W5–9   초안·2차 셀렉(B) → W9–10 LLM(C) → W7–11 프론트 → W10–12 지표 → W12–14 심사 준비
```

## 6. 멘토님께 여쭤볼 것

1. **쌍 비교 12개로 취향이 잡힐까요?** 홀드아웃 정확도가 50%와 구분 안 되면 폴백은 "별점·선택
   충분한 고객만 개인화". 다른 콜드스타트 방법 경험이 있으신지.
2. **12B vs 31B** — RTX 6000 + gemma 31B 경험에서, 웨딩 사진의 장면·구도·조명·표정 분류 수준에도
   31B가 확연히 나았는지, 아니면 12B로 충분했는지.
3. **L4(24GB)에서 12B vLLM 배치로 사진당 0.3초**가 현실적인 수치인지. 아니면 7B로 내려야 하는지.
4. **λ(사진학↔취향 가중)** 설계 — 증거량 함수로 두는 방식에 대한 의견. PIAA 쪽에서 비슷한
   관행이 있는지.
5. 온디맨드 EC2 기동 4~5분이 10분 예산의 절반 — AMI 가중치 굽기 외에 줄일 방법.
