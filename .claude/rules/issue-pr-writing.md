# 이슈·PR 본문 쓰는 법

이슈·PR 본문을 쓸 때 따른다 — `gh issue create`·`gh pr create`로 직접 만들 때도 같다. 섹션 이름은 저장소 템플릿
(`.github/ISSUE_TEMPLATE/issue-template.md`, `.github/PULL_REQUEST_TEMPLATE.md`)이 정하고, 이 문서는 **그 안을 어떻게 채우는지**를 정한다.
제목·브랜치·라벨 형식은 `git-workflow.md`가 정한다. `organic-agent-server`의 `.claude/spec/issue-pr-writing.md`와 같은 규칙이다.

목표: 처음 보는 팀원이 **10초 안에 "무엇이 왜 바뀌나"**를 알고, 1분 안에 리뷰할 곳을 찾는다.

## 다섯 가지 규칙

1. **맨 위에 한 줄 요약.** 템플릿 첫 섹션 바로 위에 `> ` 인용 한 줄로 쓴다. "무엇을 → 왜"를 한 문장에.
   - 좋음: `> 사진 폴더 배정 이름을 세부 폴더 배정으로 바꿔, 사진이 어디에 들어가는지 이름만 보고 알게 한다.`
   - 나쁨: `> refactor: DetailFolderAssignment 이름 변경 (용어집 D9, 1단계)`
2. **세 질문으로 나눈다.** 왜(문제) / 무엇을(바꾼 것) / 어떻게 확인(검증). 한 덩어리에 섞지 않는다.
3. **한 줄에 한 사실.** 괄호 안에 또 설명을 넣지 않는다. 문장이 쉼표 두 개를 넘으면 두 줄로 나눈다.
4. **바뀐 이름·동작은 표로.** `전 → 후` 두 열 표가 문단보다 빠르다. 행은 7개 이하, 넘으면 묶음별로 나눈다.
5. **처음 보는 말은 풀어 쓴다.** 내부 약어(D3, #160, V23, 1단계)는 처음 나올 때 한 번 풀이한다.
   풀이가 길면 그 말을 쓰지 않는다.

## 모양

- **주의 사항은 맨 위에 하나만.** 머지 순서·배포 조건처럼 놓치면 사고가 나는 것만 GitHub 알림으로 쓴다.
  ```markdown
  > [!WARNING]
  > wes V23 배포와 같은 때에만 머지한다. 먼저 머지하면 운영 분석이 멈춘다.
  ```
  경고는 두 줄 안. 이유가 더 필요하면 본문에서 풀고, 경고에는 "무엇을 하면 안 되는지"만 둔다.
- **칸 제목은 `###`, 묶음 제목은 굵은 글씨.** 왜·무엇을·확인 같은 칸은 `###` 소제목으로, 칸 안의 변경 묶음은 `1. **도메인 이름**`처럼 굵은 글씨로.
- **변경은 묶음 3~5개로.** 커밋 목록을 옮기지 않는다. 묶음마다 굵은 제목 한 줄 + 항목 3개 이하.
- **흐름이 바뀌면 그림 하나.** 호출 순서·데이터 흐름·상태 전이가 바뀔 때만 작은 Mermaid(노드 6개 이하)를 넣는다.
  이름만 바뀐 변경에는 그리지 않는다.
- **길면 접는다.** 본문이 화면 한 장(약 40줄)을 넘으면 세부 목록·파일 목록은 `<details><summary>자세히</summary>…</details>`로 접는다.
  요약·경고·리뷰 포인트는 접지 않는다.
- **코드 이름은 백틱, 파일 경로는 꼭 필요할 때만.** 리뷰어가 열어 봐야 하는 파일만 경로를 쓴다.

## 제목

`git-workflow.md`의 형식 `[<모듈>] <타입>: <설명>(#이슈번호)`에서 **설명은 결과를 말하는 한국어 한 구절**로 쓴다.
- 좋음: `[categorize] refactor: 연사 이름을 cluster에서 burst로 변경`
- 나쁨: `[categorize] refactor: cluster_id → burst_id, MODEL_VERSION → PIPELINE_VERSION (용어집 1단계)`

## 이슈 채우기

| 템플릿 섹션 | 무엇을 쓰나 |
|---|---|
| 1. Issue Description | **왜** — 지금 무엇이 불편하거나 틀렸는지 2~3줄. 해결책은 여기 쓰지 않는다 |
| 2. Issue Task | **무엇을** — 체크박스 3~7개. 하나가 "끝났다"고 말할 수 있는 크기로 |
| 3. 산출물 | 끝나면 무엇이 있어야 하나 — 코드·리포트·문서 갱신. 짧게 |
| 4. Related Module | 모듈 이름만 (`embedder` · `score` · `categorize` · `preference` · `notionchat`) |

이슈에는 구현 방법을 길게 쓰지 않는다. "어떻게"는 PR의 몫이다.

## PR 채우기

| 템플릿 섹션 | 무엇을 쓰나 |
|---|---|
| (맨 위) | 한 줄 요약 `>` + 필요할 때만 경고 하나 |
| 연관 이슈 | `- close #N` |
| 구현 사항 | 아래 세 칸을 이 순서로 |
| 리뷰 요구사항(있으면) | 리뷰어가 **특히 봐 줄 곳 1~3개**. 파일·함수 이름과 "왜 거기인지" 한 줄 |

제목은 세 층이다 — **템플릿 섹션 `##`(1.5em) → 칸 `###`(1.25em) → 본문(1em)**.
- 템플릿 섹션("1. 연관 이슈", "2. 구현 사항", "3. 리뷰 요구사항", 이슈의 네 섹션)은 `##`. GitHub이 `##` 아래에 밑줄을 그으므로 `---`를 따로 넣지 않는다.
- 구현 사항의 칸(왜·무엇을·확인, 배포 순서·리뷰 포인트)은 `###`.
- `####`와 굵은 글씨는 GitHub에서 본문과 같은 1em이라 칸 제목으로 쓰지 않는다. 굵은 글씨는 칸 안의 묶음 제목에만.

```markdown
### 왜
- 문제 한두 줄

### 무엇을 바꿨나
| 전 | 후 |
|---|---|
| … | … |

### 어떻게 확인했나
- 테스트: 무엇을 돌려 몇 개 통과
- 직접 확인: (했으면) 무엇을 봤는지
```

동작이 바뀌지 않는 리팩터링이면 "무엇을 바꿨나" 아래에 **"동작은 그대로"**를 한 줄로 못 박고, 그 근거(어떤 테스트가 지키는지)를 확인 칸에 쓴다.

## 예시

나쁨 — 한 항목에 여러 사실, 괄호 속 설명, 풀지 않은 약어:

```markdown
- **categorize**: 연사 `cluster_id`·`cluster_rank` → `burst_id`·`burst_rank`, `MODEL_VERSION` → `PIPELINE_VERSION`,
  모듈 `service/cluster.py` → `service/burst.py`, 결과 키 `clusters` → `bursts`(wes는 이 결과를 읽지 않는다).
```

좋음:

```markdown
> 연사를 가리키는 이름을 `cluster`에서 `burst`로 바꿔, 학습 문서의 "연사"와 코드 이름을 맞춘다.

### 왜
- `cluster`가 연사와 그룹 두 가지를 뜻해서 코드를 읽을 때 헷갈렸다.

### 무엇을 바꿨나
| 전 | 후 |
|---|---|
| `cluster_id` | `burst_id` |
| `service/cluster.py` | `service/burst.py` |
| 결과 키 `clusters` | `bursts` |

동작은 그대로다.

### 어떻게 확인했나
- categorize 테스트 43개 통과
```

## 만들기 전 자가 점검

본문을 다 쓰면 아래를 하나씩 확인하고, 걸리면 고친 뒤 **초안을 사용자에게 보여 주고 확인받은 다음** 만든다.

- [ ] 맨 위 한 줄만 읽고 무엇이 왜 바뀌는지 알 수 있다
- [ ] 제목이 세 층이다: 템플릿 섹션 `##` → 칸 `###` → 본문 (`####`·굵은 글씨는 본문과 크기가 같다)
- [ ] 한 줄에 사실이 하나다 (괄호 속 괄호, 쉼표 셋 이상 없음)
- [ ] 이름·동작 변경이 표로 정리돼 있다
- [ ] 내부 약어가 풀이 없이 나오지 않는다
- [ ] 경고는 정말 사고를 막는 것 하나뿐이다
- [ ] 화면 한 장을 넘는 부분은 접혀 있다
- [ ] (PR) 리뷰 포인트가 1~3개로 좁혀져 있다
