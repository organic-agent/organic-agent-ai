# Notion 조회 챗봇 계획 (내부 도구 · Bedrock 스파이크 겸용)

팀 Notion(인터뷰·기획·아키텍처·비용 자료)을 자연어로 빠르게 조회하는 내부용 챗봇.
동시에 **Bedrock 첫 실전 프로젝트**다 — 모델 액세스, IAM, `AnthropicBedrockMantle` 클라이언트,
tool use 루프를 여기서 검증하고, 그 코드가 이후 P2(보정 접수 에이전트)의 원형이 된다.

---

## 1. 접근 방식 결정 — RAG 없이 시작한다

두 가지 방식을 비교했다:

| | ① 에이전트 검색 (채택) | ② RAG 파이프라인 |
|---|---|---|
| 구조 | Claude가 Notion API를 도구로 직접 검색·조회 | 적재→마크다운→청킹→임베딩→벡터 저장소→검색 |
| 구축 기간 | 하루~이틀 | 수 일 (동기화·전처리 설계 포함) |
| 신선도 | 항상 최신 (실시간 조회) | 증분 동기화 없으면 낡음 |
| 전처리 | 불필요 (조회 시점 변환) | 블록 재귀·표 문장화·선별 필터 설계 필요 |
| 검색 품질 | Notion 검색 API 수준 (키워드 중심) | 시맨틱 검색 가능 |
| 질의당 비용/지연 | 툴 루프만큼 (수 회 API 호출) | 검색은 싸고 빠름 |

**Phase 1은 ①로 간다.** 이유:
- 코퍼스가 작고(한 워크스페이스) 사용자가 팀 내부 소수라, RAG의 장점(대규모·저지연 검색)이
  아직 필요 없다
- Notion의 알려진 제약(중첩 블록 재귀, 표 문장화, 초안/폐기 페이지 오염, 증분 동기화)이
  전부 **적재 파이프라인의 문제**다 — 적재를 안 하면 문제 자체가 사라진다
- 검색 품질이 부족하다고 **확인되면** 그때 ②를 얹는다 (Phase 2). 임베딩 저장소는 이미 쓰는
  pgvector를 그대로 활용 가능

## 2. Phase 1 — 에이전트 검색 챗봇

### 아키텍처

```
CLI 채팅 (python -m notionchat)
    └─ Bedrock (AnthropicBedrockMantle, tool use 루프)
         ├─ tool: search_notion(query)          Notion Search API
         ├─ tool: read_page(page_id)            블록 재귀 조회 → 마크다운 변환
         ├─ tool: query_database(db_id, filter) DB 행 → 속성 문장화
         └─ tool: list_children(page_id)        하위 페이지 목록 (구조 탐색용)
```

- **인터페이스는 CLI부터.** 가장 빨리 쓸 수 있고, 대화 루프·도구 코드는 나중에 웹/Slack을
  붙여도 그대로 재사용된다.
- **마크다운 변환은 조회 시점에** 한다. `read_page`가 블록 트리를 재귀로 받아 마크다운으로
  펴서 반환 — 사전 적재가 없으므로 rate limit은 질의당 몇 건 수준이라 문제 안 된다.
- **모든 답변에 Notion 페이지 링크를 출처로** 붙이도록 시스템 프롬프트에 강제한다.
- 초안/폐기 페이지 오염 대응: 시스템 프롬프트에 "여러 버전이 검색되면 최신 수정본을 우선하고,
  버전 충돌이 보이면 답변에 명시하라" + `read_page`가 `last_edited_time`을 함께 반환.

### 대화·에이전트 원칙 (docs/plan.md와 동일)

- 툴 루프 상한 설정 (질의당 도구 호출 N회 제한) — 폭주 방지
- structured outputs는 불필요 (자유 응답이 목적) — 단, 출처 링크 포맷은 프롬프트로 고정

### 구현 순서

1. **Bedrock 사전 조건** — ap-northeast-2 모델 목록·inference profile 확인, Model access
   신청, IAM `bedrock:InvokeModel` (CLAUDE.md의 스파이크 항목과 동일)
2. **Notion Integration** — 토큰 발급, 루트 페이지 연결, `search`·`blocks.children` 권한 확인
3. **도구 4종 구현** — Notion API 클라이언트 + 블록→마크다운 변환기(핵심 블록 타입만:
   문단·헤딩·리스트·토글·코드·표. 이미지/임베드는 "[이미지]" 플레이스홀더)
4. **tool use 루프 + CLI 채팅** — 대화 히스토리 유지, 도구 호출 로그 출력(디버깅 겸 신뢰)
5. **골든 질문 평가** — 인터뷰·기획 문서에서 답이 명확한 질문 10~15개로 정확도·출처 검증
6. (선택) 팀 공유용 인터페이스 — Slack 봇 또는 간단한 웹

### 저장 위치

`organic-agent-ai` 안의 독립 패키지(`notionchat/`)로 둔다. 제품 코드와 무관한 내부 도구지만,
`bedrock.py`(클라이언트·에러 처리)와 tool use 루프는 P2가 물려받을 공용 자산이다.

## 3. Phase 2 — 검색 품질이 부족할 때만 (조건부)

Phase 1 골든 질문 평가에서 "Notion 키워드 검색이 못 찾는" 실패가 유의미하게 나오면:

1. 대상 페이지 선별 (루트 지정 + "확정/폐기" 속성 필터)
2. 페이지 → 마크다운 적재, DB 행은 속성 문장화
3. 제목·경로·수정일 메타데이터와 함께 청킹·임베딩 → pgvector (별도 스키마, prod와 분리)
4. `last_edited_time` 기준 증분 동기화 (스케줄 또는 수동 트리거)
5. 기존 에이전트에 `semantic_search` 도구로 추가 — 구조는 그대로, 도구만 하나 늘어난다

즉 Phase 2는 재작성이 아니라 **도구 추가**다. draw.io 다이어그램·이미지는 어느 방식이든
텍스트 추출이 안 되므로, 다이어그램 설명 텍스트를 옆에 적어두는 문서 습관이 유일한 대응이다.

## 4. 리스크

- **Notion 검색 API의 재현율** — 키워드 중심이라 의미 검색에 약함. Phase 1 평가로 실측하고
  Phase 2 전환 여부를 데이터로 결정
- **깊게 중첩된 페이지의 조회 지연** — 블록 재귀 호출 수만큼 느려짐. 변환기에 깊이 제한 +
  토글 하위는 요청 시 확장
- **rate limit** — 적재가 없어 낮은 리스크. 재시도(backoff)만 기본 탑재
- **권한 경계** — Integration에 연결한 페이지만 보인다. 안 보이는 문서는 "없다"가 아니라
  "연결 안 됨"일 수 있음을 시스템 프롬프트에 명시
