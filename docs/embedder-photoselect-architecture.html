전체 그림

웨딩 사진 갤러리를 놓고 배치 세 개가 순서대로 돈다. embedder는 갤러리당 1회, 원본을 열어 미리보기 JPEG를 S3에 올리고 그 파일로 DINOv3 벡터를 계산해 EXIF와 함께 wes 공유 Postgres에 적는다. photoselect SCORE는 미리보기만 읽어 사진별 점수와 CLIP 벡터·zero-shot 라벨을 적고, photoselect CATEGORIZE는 저장된 벡터와 점수만으로(torch 없이) 연사·임베딩 그룹을 만들고 Bedrock으로 이름을 붙인다. 폴더 실체와 폴더별 추천·비교샷은 wes가 한다. 경계는 "갤러리 전수에 torch 모델 추론이 필요한가"이고, wes도 미리보기 몇 장을 읽어 Bedrock에 보낸다. 두 저장소는 HTTP로 데이터를 나르지 않는다 — DB 테이블이 곧 인터페이스다.

갤러리 잡 — job.run, 순서가 계약이다 (#24)

E0

잠금 — 갤러리 id로 세션 수준 pg_try_advisory_lock. 이미 잡혀 있으면 모델을 올리기 전에 {"skipped": "already running"}으로 끝난다. 연결이 닫히면(타임아웃 포함) 풀린다.

E1

대상 선별 — photos 중 status ≠ PENDING, 휴지통 아님, photo_analysis.embedding이 없는 것만. force면 마지막 조건을 뺀다.

E2

배치 시작 전 데드라인 검사 — 남은 시간이 "지금까지 가장 긴 배치 + STOP_MARGIN_SECONDS(60)"보다 적으면 배치 경계에서 멈추고 commit. 결과에 stopped·remaining.

E3

원본을 열어 두 갈래 — 회전 전 원본에서 EXIF(best-effort), prepare가 HEIC 디코드·회전·RGB·1024 축소. 그 다음 ① JPEG로 인코딩해 S3 PUT, ② 올린 바로 그 바이트를 open_preview로 다시 열어 DINOv3. PUT이 실패하면 encode에 들어가지 않고 그 사진은 failed다.

E4

한 트랜잭션, 배치 단위 commit — photo_analysis UPSERT는 embedding·embedding_model만. photos UPDATE는 preview_key를 덮어쓰고(이번에 올린 파일이 곧 벡터의 원본), EXIF만 COALESCE. WHERE id=? AND storage_key=? CAS로 선별 뒤 교체된 사진은 0행 갱신.

E5

자기 재호출 handler — 멈췄고 이번 실행에서 한 장이라도 처리했으면 같은 갤러리로 자기 자신을 EVENT 재호출(force 없이). 처리 0장이면 재호출하지 않는다. best-effort — 실패하면 reinvoked: false로만 드러난다.

"미리보기 없는 벡터"는 구조적으로 생기지 않는다. 벡터가 S3에 실제로 올라간 파일에서 나오므로 status='EMBEDDED'는 곧 "벡터와 미리보기가 둘 다 있다"는 뜻이고, photoselect·wes가 보는 픽셀과 벡터가 같은 파일이다. 실패는 두 종류뿐이다 — 벡터가 없으면 failed(다음 호출이 다시 집는다), EXIF만 실패하면 metadataFailed. failed가 대상 수와 같으면 임베딩이 아니라 IAM(s3:PutObject) 문제다.

배포·접속에서 알아야 할 것

배포는 deploy.sh만이 한다

  • Lambda 컨테이너 이미지 — zip 250MB 한도를 torch가 넘는다. DINOv3 가중치는 빌드 시 HF 토큰으로 굽고 런타임은 오프라인.
  • --platform linux/amd64 --provenance=false --sbom=false 셋 다 필수.
  • terraform apply도 :latest 푸시도 배포가 아니다. 다이제스트로 update-function-code 후 CodeSha256 검증.

네트워크·접속

  • 원래 RDS IAM 토큰 설계. 조직 SCP가 막아 임시로 DB_PASSWORD(apply 밖에서 주입).
  • 서브넷에 NAT가 없다. S3는 게이트웨이 엔드포인트. HF·Parameter Store·Lambda API는 접근 불가 — 자기 재호출은 인터페이스 엔드포인트가 생겨야 실제로 동작한다.

SCORE사진별 점수 — CLIP 벡터 하나로 세 가지를 얻는다

사진마다 (미리보기 JPEG 입력) LaionRunner.embed → CLIP 768d (저장: photo_analysis.clip_embedding) ├─ score_from_embedding → aesthetic_score (LAION MLP) ├─ SubjectsTagger.tag → subjects (bride|groom|couple|group, margin < 0.01 → unknown) └─ ParentTagger.tag → sub_scores.clip_parent (부모 고정 목록 argmax — 검증용 라벨) ArniqaRunner.score → technical_score (spaq 회귀기) classical.measure → sharpness · highlight_clip · shadow_clip · mean_luma → store.write_scores (subjects · sub_scores · clip_embedding · model_version 만)

텍스트 프롬프트는 추가 비용 0이라 미학·피사체·부모 라벨을 한 벡터에서 뽑는다. 부모 라벨을 사진 단위로 저장해 두는 덕에 CATEGORIZE가 CLIP 텍스트 인코더 없이 검증할 수 있다. write_scores는 백분위·클러스터·그룹 컬럼을 건드리지 않으므로 새 업로드분만 증분 처리해도 기존 그룹이 깨지지 않는다.

CATEGORIZE갤러리 그룹화 + 이름 — 경계는 임베딩, 이름은 VLM, 부모 목록은 고정

C1

입력은 전부 DB — 임베더의 DINOv3 E, SCORE의 CLIP C와 원점수·clip_parent. 미리보기 파일은 필요 없다(load_db(download=False)). 대표 사진은 naming이 preview_path로 지연 다운로드한다. 로컬 데이터셋 모드는 임베더가 없어 CLIP을 E 자리에 쓴다(embeddingsSource: clip).

C2

그룹화

백분위 technical/aesthetic_score · sharpness → *_pct (NaN → 50) 연사(burst) E, 카메라 파티션 ∧ taken_at 순 창 ≤ 8 ∧ cos ≥ 0.96 → cluster_id · cluster_rank(대표 0) 임베딩 그룹 X = normalize([ normalize(E) ⊕ normalize(C) ]) cos(X) = 두 공간 코사인의 평균 평균연결 계층 클러스터, 코사인 거리 0.2, 적응 규칙(대칭) → embed_group_id 과병합: 그룹 < 4 또는 최대 > 50% → 0.05씩 하강 (하한 0.05) 과분할: 그룹 > n×0.35 → 0.05씩 상승 (상한 +0.15), 과병합되면 되돌림 → store.write_groups (pct · cluster · group · sub_scores 만)
C3

이름 짓기 naming ② — 크기순 커버리지 85%(상한 120그룹)까지 대표 1장(spread > 0.12면 최원점 1장 추가)을 15장 청크로 Sonnet에. 부모는 PARENTS 고정 목록을 JSON 스키마 enum으로 강제, 컨셉은 열린 한국어 이름. 청크 둘 이상이면 통합 텍스트 호출 1회.

C4

소그룹 배정 naming ③ — VLM에 안 간 그룹은 concat 공간 최근접 이름 상속. 거리 > 0.25면 기타/기타 + needs_review.

C5

검증 naming ④ — 저장된 clip_parent의 그룹 다수결이 VLM 부모와 다르거나 confidence < 0.8이면 needs_review. 검증 전용 — 판정은 VLM의 것. 결과는 ai_concept_assignments에 잡 id로 매달린다.

비용 상한이 구조로 잡혀 있다. Bedrock 이미지 호출 수 ≤ ⌈대표 수/15⌉ + 1. 갤러리가 7,000장이 되어도 커버리지 목표와 그룹 상한이 정한 범위를 넘지 않는다. CATEGORIZE 전체가 torch 없이 돌아 수백 MB 이미지로 Lambda에 올리거나 wes로 옮길 수 있다.

개선을 검토할 때 볼 자리

  • 임베더 자기 재호출의 인프라. Lambda 인터페이스 VPC 엔드포인트와 자기 함수 lambda:InvokeFunction이 아직 없다. 없으면 7,000장 갤러리는 앱이 여러 번 불러야 끝난다.
  • 워커의 실행 환경이 미정. 상시 EC2 vs 온디맨드 Fargate --once. CATEGORIZE가 torch에서 풀렸으니 SCORE만 무거운 환경이 필요하다. SCORE를 embedder Lambda에 합쳐 미리보기 한 번에 DINOv3·CLIP·ARNIQA를 다 뽑는 선택지도 열려 있다.
  • wes isAnalyzed 조건. SCORE→CATEGORIZE 창에서 백분위가 null인 사진을 "분석됨"으로 본다. embedGroupId != null 추가가 후속.
  • MODEL_VERSION 하나가 SCORE 재개 키. 러너·임계값을 바꿔도 안 올리면 재점수되지 않고, 올리면 전 갤러리가 대상. 변경 규칙 미문서화.
  • 로컬 러너 리사이즈 1600 vs 미리보기 1024. DB 모드는 축소만 하니 무해하지만 로컬 실험값을 운영 임계로 옮길 때 스케일이 다르다.
  • ARNIQA torch.hub :main 참조와 LAION MLP URL 다운로드. Lambda로 갈 때 가중치 번들링·커밋 SHA 고정이 선행 조건.
  • 워커는 잡마다 러너를 다시 올린다. SCORE 안에서 LaionRunner()(890MB)·ArniqaRunner()를 매번 생성. embedder의 lru_cache 패턴이 후보.
  • 연사 0.96 · 그룹 0.2 재측정. CLIP/DINOv2 시절 실측값. categorize 결과의 similarityProfile·groupDistance가 근거.
