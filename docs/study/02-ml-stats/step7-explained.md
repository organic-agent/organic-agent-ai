`plan.md` §3-A의 전수 분석은 사진마다 이런 것들을 매긴다.

| 단계 | 산출 | 문제의 종류 |

| A-7 클러스터 대표 | `cluster_rank` | 순위 ← step9 |

01은 이 중 어느 것도 다루지 않았다. 01의 문제는 처음부터 끝까지 **쌍 비교**였고,

### 이 실습의 데이터

`abatch.py`가 A-1의 `eyes_open` 점수를 흉내 낸다.

```python
sigma = 0.5 + 0.4 / np.sqrt(np.maximum(ratio, 0.005))     # 얼굴이 작을수록 잡음이 크다
z = np.where(closed, -2.2, 2.2) + rng.normal(0.0, sigma)
score = 1.0 / (1.0 + np.exp(-z))
```

**잡음의 크기가 얼굴 비율에 반비례한다.** 이 한 줄이 스파이크 리포트의 관찰을 만든다:

> 작은 얼굴의 blink 신호 신뢰도: 2인 컷(얼굴 bbox 비율 ~0.036)에서 eyes_open 최소값이
> 0.2대로 낮게 나온다 — 실제 눈 감김인지 blendshape가 작은 얼굴에서 불안정한 건지 확인 필요.

## 1. [실험 A] 정확도가 쓸모없어지는 자리

```
얼굴이 있는 사진 825장 중 진짜 눈감김 44장 (5.3%)

검출기                      정확도    정밀도    재현율      F1
① 전부 '정상'이라고 답        0.947      nan   0.000     nan
② 전부 '눈감김'이라고 답       0.053    0.053   1.000   0.101
③ eyes_open < 0.5          0.864    0.270   0.909   0.417
```

### ①이 아무 일도 안 하는데 정확도 0.95다

**희귀 사건에서 정확도는 다수 클래스의 비율을 되풀이할 뿐이다.**
"눈감김 검출기 정확도 95%"라고 보고하면 훌륭해 보이지만, 그 검출기는 눈감김을
**한 장도 못 잡는다.** 재현율 0을 봐야 알 수 있다.

> 01 step5 [A]의 "정확도만 쓰고 표본 수를 안 쓰면 읽을 수 없는 숫자"와 같은 병이다.
> 다만 여기서는 표본 수가 아니라 **기저율(base rate)** 이 빠진 것이다.
> 다중 클래스에서는 이것이 "최빈 클래스 비율"이 된다 — step8 [A].

### 실무 규칙

> **희귀 사건에서는 정확도를 아예 보고하지 않는 편이 낫다.** 오해만 만든다.
> 정밀도·재현율·F1을 쓰고, 기저율을 함께 적는다.

③의 정확도 0.864는 ①의 0.947보다 **낮다.** 그런데 ③이 훨씬 쓸모 있다.
정확도만 보면 "검출기를 넣으면 나빠진다"는 결론이 나온다 — 정확히 반대다.

## 2. [실험 B] 혼동행렬 — 네 칸이 전부다

임계값 0.5에서:

```
                    예측: 눈감김   예측: 정상
    정답: 눈감김            40            4   ← 놓친 것(FN)
    정답: 정상             108          673
                     ↑ 잘못 잡은 것(FP)

    정밀도 40/148 = 0.270    재현율 40/44 = 0.909
```

**재현율은 0.909로 훌륭한데 정밀도는 0.270이다.** 눈감김이라고 지목한 148장 중
108장이 멀쩡한 사진이다. 이 검출기를 그대로 쓰면 **멀쩡한 사진 108장이 벌점을 받는다.**

### 0.5는 아무 근거 없는 값이다

σ의 중앙값이라서 0.5일 뿐, 우리 비용 구조와는 아무 관계가 없다.
그런데 대부분의 코드가 무심코 0.5를 쓴다. [D]에서 근거 있는 값을 고른다.

## 3. [실험 C] PR과 ROC가 다른 말을 한다

```
ROC-AUC 0.962      Average Precision(PR-AUC) 0.541
(무작위 검출기의 기준선:  ROC-AUC 0.500 ·  AP = 유병률 0.053)

임계값    예측 눈감김    정밀도    재현율      FPR
0.10          48    0.562    0.614    0.027
0.20          71    0.479    0.773    0.047
0.30          95    0.389    0.841    0.074
0.50         148    0.270    0.909    0.138
0.70         231    0.190    1.000    0.239
```

### 같은 검출기인데 두 지표가 정반대 인상을 준다

- **ROC-AUC 0.962** — "거의 완벽한 검출기"로 읽힌다
- **AP 0.541** — 기준선(0.053)의 10배지만 절대값으로는 초라하다

### 왜 갈리나 — 분모가 다르다

```
FPR   = FP / (FP + TN)     분모가 **정상 사진 전체**(781장) — 거대하다
정밀도 = TP / (TP + FP)     분모가 **눈감김이라고 한 것**(148장) — 작다
```

임계값 0.5에서 오탐이 108장인데 FPR은 0.138밖에 안 된다. 781장에 묻히기 때문이다.
반면 정밀도는 0.270으로 바로 무너진다.

> **희귀 사건에서는 PR을 본다.** ROC는 낙관적으로 보이게 만든다.
> 우리 문제에서 눈감김(5%)·특정 장면(`ring` 1.6%)처럼 희귀한 것을 다룰 때마다 해당된다.

### `plan.md`의 AUC 폐기와는 다른 이야기다

08-22에 골든셋 AUC를 폐기한 것은 **정답 라벨이 존재하지 않아서**였다("정답 셀렉"이 없다).
여기서 말하는 것은 라벨이 있는 문제(눈감김은 정답이 있다)에서 **어떤 곡선을 볼 것인가**다.
둘은 다른 층위의 결정이고, 후자는 여전히 유효한 질문이다.

## 4. [실험 D] 임계값은 비용이 정한다 — 그리고 우리는 자르지 않는다

```
C_FN : C_FP    최적 임계값    정밀도    재현율    총비용
 1 : 1            0.05      0.643    0.409       36
 3 : 1            0.21      0.486    0.795       64
10 : 1            0.36      0.374    0.909      107
 1 : 3            0.02      0.667    0.182       48
```

**비용비를 바꾸면 최적 임계값이 0.02에서 0.36까지 움직인다.**
"눈감김을 놓치는 것이 3배 비싸다"는 **제품 결정**이고, 데이터가 답해 주지 않는다.
그 결정을 안 하고 0.5를 쓰면 **암묵적으로 어떤 비용비를 가정한 것**이다 — 모른 채로.

### ★ 그런데 우리 설계는 애초에 자르지 않는다

CLAUDE.md: **품질 점수로 하드 필터링 금지.** 그럼 `eyes_open`을 어디에 쓰나?
`plan.md` §3-A가 이미 답을 갖고 있다.

```
① 사진학 prior의 재료      — 순위를 흔들 뿐 후보를 없애지 않는다
② 클러스터 대표 선정 (A-7)  — 연사 5장 중 눈 뜬 컷을 고른다
```

**②가 이 신호의 진짜 쓰임새다.** 그리고 ②는 **절대 판정이 아니라 상대 비교**다 —
"이 사진이 눈감김인가"가 아니라 "같은 연사 안에서 누가 더 눈을 떴나".

> **임계값이 아예 필요 없다.** 정밀도·재현율도 필요 없다. 필요한 것은 **순위**뿐이다.

### 이 스텝에서 가장 중요한 한 줄

> **분류 문제로 보이는 것이 사실은 순위 문제일 때가 있다.**

문제를 어떻게 세우느냐가 필요한 지표를 정한다. 우리가 "눈감김 검출기의 정확도"를
목표로 잡았다면 라벨링·임계값·비용 분석에 몇 주를 썼을 것이다.
"연사 안에서 대표 고르기"로 세우면 그 작업이 통째로 사라진다.

(step9 [B]가 같은 이야기를 확률 쪽에서 한 번 더 한다 — 순위만 쓰면 보정도 필요 없다)

## 5. [실험 E] 스파이크 리포트의 미해결 관찰을 푼다

```
얼굴 bbox 비율        장수   뜬눈 점수 중앙값   뜬눈 최소   ROC-AUC      AP
~0.05 (단체·풍경)     215          0.92      0.00     0.935   0.323
0.05~0.12 (전신)     282          0.89      0.01     0.950   0.560
0.12~0.25 (상반신)    225          0.89      0.08     0.985   0.874
0.25~ (클로즈업)      103          0.90      0.44     1.000   1.000
```

### 뜬눈 점수의 중앙값은 얼굴 크기와 거의 무관하다

`0.92 / 0.89 / 0.89 / 0.90`. **작은 얼굴이라고 점수가 낮아지는 게 아니다.**

달라지는 것은 **최소값**(0.00 → 0.44)과 **분리도**(AP 0.323 → 1.000)다.

### 그래서 스파이크 리포트의 관찰은 이렇게 읽어야 한다

> "2인 컷에서 eyes_open 최소값이 0.2대로 낮게 나온다"

**점수가 낮은 것이 아니라 분산이 큰 것이다.** 그리고 둘은 처방이 다르다.

| 진단 | 처방 | 비용 |
|---|---|---|
| 작은 얼굴에서 점수가 **낮다** | 임계값을 얼굴 크기별로 다르게 | 싸다 |
| 작은 얼굴에서 점수가 **흔들린다** | 얼굴 크롭 후 재검출 | 원가 상승 (리포트가 우려한 그것) |

**최소값 하나로는 둘을 못 가른다.** 이 표를 뽑아야 갈린다.

### 그래서 무엇을 해야 하나

스파이크 리포트의 "확인 필요" 항목에 필요한 작업이 명확해진다.

```
작은 얼굴(bbox < 0.05) 사진 50장에 눈감김 라벨을 달고
얼굴 크기 구간별 AP를 실제로 뽑는다.
```

라벨 50장이면 된다. "최소값이 0.2대"를 몇 번 더 들여다보는 것으로는 답이 안 나온다.

> **그리고 [D]를 기억하면 이 작업의 우선순위가 내려간다.** 우리는 임계값으로
> 자르지 않고 클러스터 안에서 순위만 쓴다. 순위는 **같은 연사 안에서** 비교하므로
> 얼굴 크기가 대체로 비슷하다 — 즉 이 문제의 영향을 가장 덜 받는 사용법이다.
> 라벨링은 `eyes_open`을 prior에 넣는 가중치를 정할 때 하면 된다.
