`lab/step9_calibration.py` 해설 · 2026-08-25

> 02 step2 [A]는 이렇게 끝났다 —
> **"정확도가 못 보는 변화가 있다. 확률값을 쓰는 곳에서는 그 차이가 드러난다."**

## 0. 보정이란

모델이 "0.8"이라고 말한 사진들을 모아 보니 실제로 80%가 양성이면
**보정됐다(calibrated)** 고 한다. 90%거나 60%면 안 된 것이다.

```
신뢰도 도표(reliability diagram)
  예측 확률을 구간으로 묶고 구간마다 (평균 예측, 실제 비율)을 찍는다. 대각선이면 완벽.

ECE(Expected Calibration Error)
  Σ (구간 비중) × |평균 예측 − 실제 비율|
```

### 보정과 순위는 독립이다 — 이 스텝의 축

점수에 **단조 함수**를 씌우면 순위가 안 바뀐다. 따라서 AUC·AP는 그대로인데
보정은 완전히 달라진다. 반대도 마찬가지다.

> **"AUC가 높으니 확률을 믿어도 된다"는 틀린 추론이다.**
> 두 성질은 서로를 보장하지 않는다.

## 1. [실험 A] eyes_open은 확률이 아니다

```
 예측 구간 평균   실제 뜬눈 비율   표본 수      차이
        0.045          0.438       48   −0.392  ←
        0.153          0.696       23   −0.543  ←
        0.265          0.875       24   −0.610  ←
        0.454          1.000       35   −0.546  ←
        0.650          0.977       43   −0.327  ←
        0.858          1.000      142   −0.142  ←
        0.964          1.000      380   −0.036

ECE = 0.188
```

### 전 구간이 한쪽으로 어긋난다

예측보다 실제 뜬눈 비율이 **항상 높다.** 점수 0.045짜리 사진들 중에서도 44%가
실제로는 눈을 뜨고 있다.

### 주된 원인은 기저율이다

눈감김이 5%뿐이라 **점수가 낮아도 대부분은 여전히 뜬 눈이다.**
그런데 σ(z)는 그 사전 정보를 전혀 안 쓴다 —
"이 사진이 얼마나 감은 눈처럼 보이나"를 잴 뿐 "얼마나 감았을 확률인가"가 아니다.

여기에 작은 얼굴의 잡음(step7 [E])이 얹혀 낮은 구간을 더 흐린다.

> **모델의 출력이 [0,1] 범위라고 해서 확률이 아니다.**
> sigmoid를 통과했다는 것은 스케일 이야기지 의미 이야기가 아니다.
> MediaPipe의 blendshape 점수, ARNIQA의 0~1 점수 전부 같은 처지다.

### 결론

이 점수는 **순위로는 쓸 만한데(AUC 0.96) 확률로는 못 쓴다(ECE 0.19).**

## 2. [실험 B] 보정 — 그리고 보정이 바꾸지 않는 것

절반으로 보정 함수를 적합하고 나머지 절반에서 잰다.

```
방법                  ECE   ROC-AUC   AP(눈감김)
원본                0.191     0.956      0.543
Platt scaling      0.030     0.956      0.543
Isotonic           0.034     0.917      0.500
```

### ECE는 6배 줄고 ROC-AUC·AP는 소수점까지 그대로다

Platt scaling은 **로지스틱 함수 하나**(파라미터 2개)를 씌운 것이다. 단조 함수이므로
순위가 하나도 안 바뀐다 — `0.956`, `0.543`이 소수점 셋째 자리까지 같다.

**두 가지가 따라온다.**

```
① "AUC가 높으니 확률을 믿어도 된다"는 틀린 추론이다
② 순위만 쓰는 곳에서는 보정이 아무 의미가 없다
```

②가 우리에게 중요하다. step7 [D]에서 봤듯 `eyes_open`의 진짜 쓰임새는
**클러스터 대표 선정**이고, 그건 순위다. **거기서는 보정할 필요가 없다.**

### Isotonic이 왜 AUC를 떨어뜨렸나

`0.956 → 0.917`. Isotonic은 계단 함수라 **같은 값으로 묶이는 구간(ties)이 생긴다.**
묶이면 그 안에서 순위 정보가 사라진다. 유연한 대신 정보를 버리고, 표본이 적으면
과적합한다.

> **우리 규모에서는 Platt이 안전하다.** 갤러리당 수백~수천 장이지만
> 눈감김 라벨은 그중 일부만 붙일 수 있고, 파라미터 2개짜리 모델이 그 규모에 맞는다.

## 3. [실험 C] `plan.md`가 백분위를 쓰는 이유

설계안 §3-A/§3-B의 점수는 전부 **갤러리 내 백분위**다.

```
prior(p) = technical_pct·w_t + aesthetic_pct·w_a
```

| | ARNIQA 원점수 | 백분위 |
|---|---|---|
| 실측 관측 대역 | 0.49 ~ 0.52 | 0 ~ 100 |

### 백분위 변환은 순위 보정이다

원점수의 절대값이 무슨 뜻인지 몰라도, **같은 갤러리 안에서 몇 등인지는 확실하다.**

왜 안전한 선택인가:

1. **ARNIQA와 LAION은 단위가 다르다** (0~1 vs AVA 1~10). 그대로 더할 수 없다
2. 두 모델 다 확률로 보정돼 있지 않다. 보정하려면 **라벨이 필요한데 없다**
3. 백분위는 라벨 없이 되고, **단조 변환이라 순위 정보를 안 버린다**

> 즉 **보정이 필요한 문제를 보정이 필요 없는 문제로 바꾼 것**이다.
> [B]②와 같은 사고다 — 순위로 쓰면 보정이 필요 없다.

### 대가

**갤러리 간 비교가 불가능해진다.** 갤러리 A의 백분위 90과 갤러리 B의 90은 다른 품질이다.
우리 문제에서는 갤러리 안에서만 고르므로 무해하지만,
"이 갤러리는 전반적으로 잘 찍혔다" 같은 판단은 못 한다.

> 스파이크 실측 메모가 이미 관련 위험을 적어 뒀다 —
> *"10장 샘플이라 분산이 작다. 전수 실행에서 갤러리 내 백분위의 변별력 확인이 본 게임"*
> **원점수 대역이 좁으면(0.49~0.52) 백분위가 잡음의 순위가 된다.**
> 백분위는 스케일 문제를 풀지만 **신호가 없는 것을 있게 만들지는 못한다.**

## 4. [실험 D] 02 step2 [A]의 미해결 질문에 답한다

Bradley-Terry는 확률을 뱉는다: `P(i를 고름) = σ(margin)`. 그 확률이 맞나?

```
reg      홀드아웃 정확도     ECE   평균 확신도   진단
0.03            0.611   0.195     0.803   과신(over-confident)
0.1             0.613   0.165     0.774   과신
0.3             0.612   0.120     0.729   과신
1.0             0.616   0.049     0.661   대체로 맞음
3.0             0.611   0.025     0.597   대체로 맞음
10.0            0.610   0.063     0.543   과소(under-confident)
30.0            0.610   0.089     0.517   과소
```

### 정확도는 0.610~0.616에 갇혀 있는데 확신도는 0.803에서 0.517까지 움직인다

**같은 정확도에서 모델이 얼마나 확신하는지가 완전히 다르다.**

```
reg 작음  →  w가 커진다  →  margin이 커진다  →  확률이 0/1로 몰린다  =  과신
reg 큼    →  w가 작아진다 →  margin이 작아진다 →  확률이 0.5로 몰린다  =  과소
```

02 step2 [A]에서 "정확도가 못 보는 변화"라고만 했던 것의 **정체가 이것이다.**

### 그리고 reg=1.0~3.0이 보정도 최적이다

step2 [A]에서 편향²+분산의 합이 최소인 지점이 **reg=1.0**이었다.
여기서 ECE가 최소인 지점은 **reg=1.0~3.0**이다.

> **두 개의 독립적인 기준이 같은 값을 가리킨다.** 01이 reg=1.0을 쓴 것은
> 근거 없는 선택이었지만, 사후적으로 두 방향에서 정당화됐다.
> (그리고 "우연히 맞았다"와 "근거가 있다"는 다르다 — 이제는 후자다)

### 과신이 왜 위험한가

우리 시스템에서 BT의 확률이 직접 쓰이는 자리는 많지 않다. 그런데 **간접적으로는 있다**:

- `pref`를 z-표준화하기 전의 분포 모양 — 과신하면 극단값이 많아져 표준화 후에도 쏠린다
- conf(axis)의 승/패 판정 — 마진이 클수록 판정이 뒤집히기 어렵다
- 이유 문장의 강도 — [E]

## 5. [실험 E] 이유 문장은 확률을 소비한다

설계안 §3-C: 이유 문장은 템플릿이고 LLM은 **선택을 바꿀 수 없다.**
그런데 템플릿의 **강도**는 확률에서 온다.

| 문장 | 필요한 것 |
|---|---|
| "서약 장면이라 골랐어요" | `scene` 태그의 **정밀도** (step8 [B]) |
| "자연광을 선호하셔서" | 그 축 conf + **다중 비교 보정** (step5 [A]) |
| "눈을 감지 않은 컷이라" | `eyes_open`의 **보정된 확률** (이 스텝 [A]) |
| "이 순간의 대표 컷이에요" | **순위만 있으면 된다** — 보정 불필요 |

### 마지막 줄이 요점이다

**같은 신호라도 순위로 쓰면 보정이 필요 없고, 단언으로 쓰면 필요하다.**

지금 우리 `eyes_open`은 ECE 0.19라 두 번째 용법에 쓸 수 없다. 선택지는 둘이다.

```
① 라벨을 붙여 Platt 보정을 한다        (라벨 비용)
② 문장을 순위형으로 바꾼다             ("이 순간의 대표 컷이에요")
```

②가 싸고, 우리 파이프라인의 실제 동작(A-7 클러스터 대표)과도 정확히 맞는다.

> **되먹임**: 이유 문장 템플릿을 만들 때 **각 문장이 요구하는 근거의 종류**를 함께 적어 둔다.
> `정밀도가 필요한 문장 / conf가 필요한 문장 / 순위면 되는 문장`.
> 그러면 "이 문장을 쓸 수 있나"가 감이 아니라 **확인 가능한 조건**이 된다.

## 7. 02 영역을 닫으며 — 아홉 스텝의 지도

```
step1  구간·커버리지      "이 숫자를 얼마나 믿나"        ← 추론통계
step2  편향-분산          "무엇을 사고파나"             ← ML
step3  경험적 베이즈       "상수를 데이터에서"            ← ML/통계
step4  승자의 저주        "고른 데이터로 자랑하지 않기"    ← ML
step5  다중 비교          "여러 번 보면 뭔가는 나온다"     ← 추론통계
step6  리포트            "전부 적용하면"                ← 종합
─────────────────────────────────────────────────────────
step7  분류 지표·임계값    A-1 눈감김                    ← ML (전수 분석)
step8  혼동행렬          A-4 VLM 태그                  ← ML (전수 분석)
step9  확률 보정         A-2/A-7 점수 결합              ← ML (전수 분석)
```

**step1~6은 01의 숫자를 판정했고, step7~9는 A 배치를 다룬다.**
소재가 다르고 문제의 종류가 다르다 — 추천이 아니라 분류·순위·확률이다.

### 세 스텝이 관통하는 한 가지

```
step7 [D]  분류로 보이는 것이 순위 문제일 수 있다  →  임계값이 필요 없어진다
step9 [B]  순위만 쓰면 보정이 필요 없다           →  라벨이 필요 없어진다
step9 [C]  백분위는 라벨 없는 순위 보정           →  스케일 문제가 사라진다
```

**우리 설계가 계속 순위로 도망치는 것은 우연이 아니다.**
정답 라벨이 없는 문제(01의 출발점)에서는 절대 판정을 할 수 없고,
할 수 있는 것은 **같은 갤러리 안에서의 상대 비교**뿐이기 때문이다.
