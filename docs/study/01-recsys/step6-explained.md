## 0. 이 스텝이 증명하는 것과 증명하지 못하는 것

먼저 경계를 그어 두고 시작한다. 안 그러면 마지막에 잘못된 자신감을 얻는다.

| | |
|---|---|
| ✅ 증명할 수 있다 | **배관이 이어졌다.** 라운드마다 evidence·λ·점수·재랭킹이 실제로 갱신된다 |
| ✅ 증명할 수 있다 | 각 조각의 **인터페이스가 맞는다.** step3의 conf가 step4의 입력으로 들어간다 |
| ❌ 증명할 수 없다 | **서비스가 설득력 있다.** 고객이 코드다 — 수락률은 내가 쓴 가정의 되풀이다 |
| ❌ 증명할 수 없다 | 실제 부부가 몇 라운드 만에 끝내는가, 만족하는가 |

**고객이 코드라는 것**이 핵심 제약이다. `customer_accepts`는 이렇게 생겼다.

```python
p = 1.0 / (1.0 + np.exp(-(sat[idx] - threshold) / ACCEPT_TEMP))
return rng.random(len(idx)) < p
```

만족도가 높으면 담을 확률이 높다 — 내가 그렇게 정했으니 그렇게 된다.
**이 루프가 "고객이 좋아한다"를 보여 줄 수는 없다.** 보여 줄 수 있는 것은
"내가 정의한 만족도를 높이는 방향으로 시스템이 실제로 움직인다"까지다.

> 진짜 수치는 사람에게 받은 쌍에서만 나온다 — 그게 step5에서 설계한 W1–2 실험이다.

## 1. 파이프라인 — 설계안 §3-B와 1:1

```
① 온보딩 12쌍            → BT로 취향 벡터 추정              (step1·2)
② λ(evidence)·conf(axis) → prior와 취향을 섞어 점수          (step3)
③ 커버리지 + 클러스터 + MMR → 제시할 30장                    (step4)
④ 고객 반응(수락/거부)     → 쌍으로 바꿔 evidence에 추가
⑤ 자연어 피드백           → {axis, tag, delta}로 번역        (LLM 자리)
⑥ 다시 ②로. 이미 담은 사진은 제외
```

코드로 보면 라운드 한 번이 이렇다.

```python
d = np.array([g.X[c] - g.X[r] for c, r in zip(chosen, rejected)])   # ①
w_hat = fit_bt(d, reg=1.0)
conf = axis_confidence(g, w_hat, ...)                                # ②
lam = lambda_of(len(chosen))
pref = z(pref_scores(g, w_hat, conf) + g.X @ nl_delta)               # ⑤가 여기 합류
score = (1 - lam) * prior + lam * pref
score[list(taken)] = -np.inf                                         # ⑥ 이미 담은 것 제외
shown = select_with_coverage(g, score, ROUND_K, lam_mmr=0.7)         # ③
```

**step1~4에서 만든 함수를 그대로 부른다.** 새로 짠 것은 고객 시뮬레이터와
피드백 번역기뿐이다. 조각이 진짜 조각이었는지가 여기서 판정된다.

> `score[list(taken)] = -np.inf` 한 줄에 주목. **이미 담은 사진은 다시 제시하지 않는다.**
> 당연해 보이지만 `plan.md` §3-B에는 이 규칙이 명시돼 있지 않다 —
> 후보 집합 정의는 아직 문서에 없는 상태다.

## 2. [실험 A] 한 사람의 4라운드

```
라운드  evidence    λ   제시  수락  수락률   nDCG    ILS  장면  자연어 피드백
  1         12  0.55    30    14   0.47  0.840  0.069   12  "full 그만"    → {framing, full, −0.09}
  2         26  0.67    30    23   0.77  0.959  0.057   12  "laugh 그만"   → {expression, laugh, −0.06}
  3         33  0.70    30    16   0.53  0.773  0.070   12  "detail 그만"  → {scene, detail, −0.12}
  4         47  0.74    30    25   0.83  0.986  0.078   12  "backlit 그만" → {lighting, backlit, −0.08}
```

### 읽을 것 — evidence와 λ가 실제로 움직인다

`12 → 26 → 33 → 47`. 온보딩 12쌍으로 시작해서 **고객의 반응이 evidence가 된다.**
λ가 `0.55 → 0.74`로 오른다 = 라운드가 갈수록 취향에 더 걸고 사진학에 덜 건다.

step3에서 만든 λ 곡선이 **여기서 처음으로 시간축을 갖는다.** [A]~[D]에서는
"증거 n개일 때"라는 정적인 표였는데, 실제 서비스에서 n은 라운드마다 커지는 값이다.

### 장면 12종이 모든 라운드에서 유지된다

커버리지가 하드 제약이라 라운드가 바뀌어도 무너지지 않는다.
이미 담은 사진이 빠져 후보가 줄어드는데도 12종을 지킨다 — 설계 의도대로다.

### 그리고 수락률이 0.47 → 0.83으로 오른다

**여기서 멈추면 안 된다.** "피드백 루프가 작동한다"고 결론 내고 싶어지는 표인데,
step5를 배웠으니 먼저 물어야 한다 — **이거 재현되나?**

## 3. ④ 반응을 '쌍'으로 바꾸는 것

`plan.md`는 👍/👎·수락/거절을 evidence에 넣는다고만 적혀 있다. 어떻게?

```python
acc_idx = [s for s, a in zip(shown, accepted) if a]      # 담은 것
rej_idx = [s for s, a in zip(shown, accepted) if not a]  # 안 담은 것
for a_i, r_i in zip(acc_idx, rng.permutation(rej_idx)[:len(acc_idx)]):
    chosen.append(a_i); rejected.append(r_i)
```

**같은 라운드 안에서** 수락 한 장과 거부 한 장을 짝지어 "이걸 저것보다 좋아했다"로 만든다.
BT는 쌍만 먹으므로 이 변환이 있어야 반응을 학습에 쓸 수 있다.

### 왜 '같은 라운드 안에서'인가

라운드가 다르면 **제시된 맥락이 다르다.** 3라운드의 거부는 "이미 좋은 걸 다 담아서
남은 것 중에 거부"일 수 있는데, 1라운드의 수락과 비교하면 그 차이가 취향으로 오해된다.
같은 라운드 안에서 짝지으면 **제시 시점·후보 풀이 같아 교란변수가 준다** —
step2 §4에서 온보딩 쌍에 "같은 scene·품질 근접" 조건을 건 것과 같은 사고다.

### 함정 — 이 쌍은 온보딩 쌍과 성질이 다르다

| | 온보딩 쌍 | 반응 쌍 |
|---|---|---|
| 두 사진의 관계 | 같은 scene, **한 축만** 다름 | 아무 관계 없음 |
| 품질 차이 | 백분위 15 이내 | 제한 없음 |
| 무엇을 배우나 | 그 한 축의 취향 | **섞여 있다** |

**반응 쌍은 랜덤 쌍에 가깝다.** step2 실험 C에서 본 그대로 —
"화질이 좋아서 담은 건지 클로즈업이라서 담은 건지" 구분되지 않는다.

그래서 evidence 수를 셀 때 온보딩 쌍과 반응 쌍을 **같은 1개로 세는 것은 낙관적이다.**
λ 곡선의 입력을 부풀리는 셈이다. 실습은 단순화를 위해 같게 셌지만,
실제로는 반응 쌍에 가중치를 낮춰 세는 것이 맞다.

> **되먹임 후보**: `λ = f(evidence)`의 evidence는 **신호 종류별 가중합**이어야 한다.
> 온보딩 쌍 1.0, 별점 1.0, 반응 쌍 0.3~0.5 같은 식. 지금 설계안은 "개수"라고만 돼 있다.

## 4. ⑤ 자연어 피드백 — LLM이 만질 수 있는 것의 경계

실제로는 고객이 *"클로즈업이 너무 많아요"* 라고 쓰고 Bedrock Haiku가
`{axis, tag, delta}` 구조체를 돌려준다(설계안 §3-C). 실습은 그 자리를 규칙으로 채웠다.

```python
gap = shown_n / len(shown) - acc_n / max(accepted.sum(), 1)
#     └─ 많이 보여줬는데 ─┘   └─ 안 담긴 태그 ─┘
```

"보여준 비중"과 "담긴 비중"의 차이가 가장 큰 태그를 찾아 음수 delta를 준다.
`shown_n < 4`면 건너뛴다 — **몇 장 안 보여준 태그로는 불평하지 않는다**(표본이 작다).

### 가드레일 — LLM은 선택을 바꿀 수 없다

```python
pref = z(pref_scores(g, w_hat, conf) + g.X @ nl_delta)
#                                       └─ 태그 가중치에만 더해진다 ─┘
```

자연어 피드백은 **점수식의 한 항으로만** 들어간다. 사진을 직접 넣거나 빼지 못한다.
설계안 §3-C가 *"LLM은 선택을 바꿀 수 없다"* 로 못 박은 것이 코드에서 이 모양이다.

> **왜 이렇게까지 하나.** LLM이 photo_id를 직접 돌려주게 하면
> 존재하지 않는 id, 이미 담은 사진, 품질 최하 컷이 섞여 들어온다. 검증 코드가 필요해지고
> 그 검증은 결국 점수식을 다시 만드는 일이 된다. **처음부터 축 가중치만 받으면
> 잘못된 값이 와도 순위가 조금 흔들릴 뿐 사고가 안 난다.**

### 이 규칙의 위험 — 노이즈를 취향으로 오해한다

2라운드의 `"laugh 그만"`을 보라. 고객이 정말 웃는 사진을 싫어하는가,
아니면 **그 라운드에 우연히 laugh 사진이 덜 담긴 것**인가?

30장 중 몇 장으로 계산한 gap이다. 수락은 확률적이므로 **한 라운드의 분포는 흔들린다.**
그런데 delta는 누적된다(`nl_delta[...] += delta`) — 잘못 짚으면 계속 깎인다.

**변형 과제**: `main()`에서 `nl_delta` 갱신을 끄고 [B]를 다시 돌려 보라.
직접 재 보면 4라운드 수락률이 `0.657 → 0.633`, R1→R4 개선이 `13/20 → 10/20`으로
내려간다 — **방향은 맞지만 20명으로도 유의하지 않다.** 실제 사람의 문장은
이 규칙보다 정확할 테니 서비스에서는 더 나을 수 있다. 다만 **여기서 얻은 숫자로
"자연어 피드백이 효과 있다"고 말할 수는 없다.**

## 5. [실험 B] 한 사람으로 읽으면 안 된다 — 수락률의 배신

같은 루프를 **고객 20명**에게 돌렸다.

```
라운드  evidence    λ   수락률   홀드아웃 정확도   남은 풀 평균    lift
  1         12  0.55   0.627         0.545        0.000   1.142
  2         23  0.65   0.613         0.595       −0.030   1.199
  3         33  0.70   0.617         0.601       −0.060   1.282
  4         44  0.73   0.657         0.606       −0.092   1.320

R1 → R4에서 개선된 고객 수 (n=20, 이항검정)
  수락률           13/20   p=0.1316
  홀드아웃 정확도    17/20   p=0.0013   ★
  lift            14/20   p=0.0577
```

### ① [A]의 상승은 시드 하나의 우연이었다

`0.47 → 0.83`이 20명 평균으로는 `0.627 → 0.657`이다. 이항검정 p=0.13 —
**우연과 구분되지 않는다.** [A]의 라운드별 수락률을 Wilson 구간으로 보면 바로 보인다.

```
R1  14/30 = 0.47  [0.30, 0.64]
R3  16/30 = 0.53  [0.36, 0.70]   ← R1과 거의 완전히 겹친다
```

**step5를 안 배웠다면 [A]의 표를 "피드백 루프가 작동한다"는 근거로 리포트에 썼을 것이다.**
그리고 멘토에게 "n이 몇이죠?"라고 질문받는 순간 방어할 것이 없었을 것이다.

### ② 그런데 루프는 실제로 작동하고 있다

**홀드아웃 쌍 정확도가 `0.545 → 0.606`, 20명 중 17명에서 개선(p=0.0013).**
이건 유의하다. 라운드마다 evidence가 쌓여 취향 추정이 **진짜로** 좋아진다.

라운드별 홀드아웃 정확도는 **학습에 안 쓴 200쌍**으로 잰다. 즉 제시한 30장이
무엇이든, 사진이 얼마나 남았든 상관없는 값이다.

### ③ 왜 수락률에는 안 나타나는가 — 두 힘이 상쇄된다

```
(+) evidence가 쌓여 취향 추정이 좋아진다      →  홀드아웃 0.545 → 0.606
(−) 좋은 사진부터 담아 가서 남은 풀이 나빠진다  →  남은 풀 평균 0.000 → −0.092
────────────────────────────────────────────────────────────────────
    수락률 = 두 힘의 합                       →  0.627 → 0.657 (거의 평평)
```

**수락률은 무엇이 일어났는지 말해 주지 못한다.** 좋아져도 나빠져도 이유를 모른다.
`lift`(제시한 30장의 만족도 − 남은 풀의 평균 만족도)를 보면 `1.142 → 1.320`으로
꾸준히 오른다 — 나빠지는 풀에서 **점점 더 잘 골라내고 있다**는 뜻이다.

### ④ 지표를 고르는 규칙

> **라운드 품질은 풀 고갈에 영향받지 않는 지표로 재야 한다.**

| 지표 | 풀 고갈의 영향 | 라운드 비교에 |
|---|---|---|
| 수락률 | **받는다** (라운드마다 후보가 나빠진다) | 부적합 |
| lift | 안 받는다 (남은 풀 기준으로 정규화) | 적합 |
| 라운드별 홀드아웃 정확도 | 안 받는다 (별도 쌍으로 측정) | 적합 |

`plan.md` §6은 *"수락률 @round — 1차→2차 상승 = 피드백이 작동"* 이라고 적어 뒀다.
**그 해석이 틀릴 수 있다는 것이 [B]의 결론이다.** 수락률이 안 올라도 루프는
작동하고 있을 수 있고, 올라도 그건 풀 구성이 바뀐 결과일 수 있다.

> **되먹임 후보**: 라운드 지표에 **lift 또는 라운드별 홀드아웃**을 추가한다.
> 수락률은 계속 보되 **단독 판정 근거로 쓰지 않는다.**
