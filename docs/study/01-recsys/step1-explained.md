## 이 문서 전체를 관통하는 예시

**부부 한 팀**이 갤러리 320장을 받았다. 이 부부의 (아직 아무도 모르는) 진짜 취향은 이렇다:

| 태그 | 이 부부의 가중치 | 뜻 |
|---|---|---|
| `framing=closeup` | **+0.8** | 클로즈업 좋아함 |
| `framing=wide` | −0.3 | 와이드는 별로 |
| `expression=smile` | **+1.2** | 웃는 얼굴을 제일 좋아함 |
| `lighting=backlit` | −0.5 | 역광 싫어함 |
| `subjects=group` | −0.7 | 단체사진 별로 |

이 5개 숫자를 묶은 것이 **취향 벡터 `w`** 다. 우리가 온보딩 12쌍으로 알아내려는 대상이 정확히 이것이다.

갤러리에서 사진 4장을 골라 보자. 각 사진은 태그 0/1 벡터 **`x`** 로 표현된다
(순서: `[closeup, wide, smile, backlit, group]`).

| 사진 | 설명 | `x` | 점수 `u = w·x` |
|---|---|---|---|
| **P1** | 신부 클로즈업, 활짝 웃음, 자연광 | `[1,0,1,0,0]` | 0.8 + 1.2 = **2.0** |
| **P2** | 역광 실루엣 반신, 웃음 | `[0,0,1,1,0]` | 1.2 − 0.5 = **0.7** |
| **P3** | 하객 단체사진, 와이드 | `[0,1,0,0,1]` | −0.3 − 0.7 = **−1.0** |
| **P4** | 신랑 클로즈업, 진지한 표정 | `[1,0,0,0,0]` | **0.8** |

**이 표가 STEP 1의 전부다.** `w`(취향)와 `x`(사진)를 곱해서 `u`(점수)를 만드는 것.
문제는 `w`를 아무도 안 알려준다는 것이고, 부부가 남기는 건 "이 둘 중엔 이게 낫다"는 판정뿐이다.

## 0. 이 스텝은 파이프라인의 어디인가 — 무엇을 만들고 무엇을 안 만드나

### 장면

부부가 로그인해서 갤러리를 연다. 그 전에 이미 벌어진 일과, 그 다음에 벌어질 일이 있다.

```
① 사진 업로드 직후 (갤러리당 1회, GPU EC2)
   원본 → preview_key(JPEG) → VLM 태그 + 경량 점수 + 임베딩
   결과: photo_analysis 테이블에 320행
   ▶ 이게 "이미지 → x" 다. 배치 A의 일.

② 온보딩 (부부가 화면에서 12번 클릭)
   "이 둘 중 어느 쪽이 마음에 드세요?"  → pair_comparison_events 12행
   ▶ 이게 "쌍 비교 기록" 이다.

③ ★ STEP 1이 다루는 곳 ★
   x(320장분) + 쌍 12개  →  w (숫자 5개, 실제로는 33개)
   ▶ 학습. 여기서 나오는 산출물은 오직 w 하나.

④ 점수 매기기
   320장 전부에 점수 계산 → 정렬
   ▶ 실제로는 u = w·x 가 아니라 (1−λ)·사진학 + λ·취향 이다. 6절에서 다룬다.

⑤ 목록 만들기 (step4)
   커버리지(장면 골고루) + MMR(비슷한 것 빼기) + 클러스터 중복 제거
   결과: ai_recommendations 테이블에 상위 N행
```

### 헷갈리기 쉬운 점 두 가지

**(1) STEP 1은 이미지를 안 만든다, 안 읽는다.** "사진에서 추천용 데이터를 뽑는 일"은 ①(배치 A)이다.
STEP 1은 `x`가 **이미 있다고 치고** 시작한다.

**(2) STEP 1은 추천 목록도 안 만든다.** 쌍 비교를 토너먼트처럼 계속 시켜서 우승자를 뽑는 게 아니다.
쌍은 **재료**고, 산출물은 `w` 하나다. `w`가 있으면 320장 전부에 한 방에 점수가 붙는다.

### 그래서 step1_bt.py는 난수를 쓴다

```python
X = RNG.normal(size=(N_ITEMS, D))   # 그냥 난수 200×5. 태그도 임베딩도 아니다
```

합성 갤러리(`gallery.py`)조차 안 쓴다. **의도적**이다.
STEP 1이 확인하려는 건 "사진이 무엇이든 상관없이 참인 성질"이기 때문이다.
여기서 태그를 썼다가 결과가 잘 나오면, **태그가 좋아서인지 수학이 성립해서인지 구분이 안 된다.**
난수로 확인해야 정직하다. 태그 33차원·임베딩 768차원은 step2의 주제다.

### 자가 점검
- STEP 1의 산출물을 한 단어로 말하면? → `w`
- "이미지 → 추천 가능한 데이터"는 어느 단계? → 배치 A(①), STEP 1이 아님

## 1. 왜 쌍 비교인가 — BT 원형이 푸는 문제

### 장면

부부에게 이렇게 물어볼 수도 있었다.

> "이 사진에 별점을 몇 점 주시겠어요?" ⭐️⭐️⭐️⭐️☆

문제가 많다. 사람마다 후한 정도가 다르고(누구는 다 4점, 누구는 다 2점), 같은 사람도
10장째와 200장째의 기준이 달라지고, 320장을 다 매기게 하면 도망간다.

대신 이렇게 묻는다.

> "이 둘 중 어느 쪽이 더 마음에 드세요?"  [P1] vs [P2]

훨씬 쉽고, 빠르고, 일관적이다. **그런데 문제가 생긴다.** 우리가 원하는 건 320장 각각의
**점수**인데, 손에 들어오는 건 "P1이 P2보다 낫다" 같은 **상대 판정**뿐이다.

> **BT 모델이 푸는 문제: 상대 판정 기록만 가지고 절대 점수를 복원하기.**
> (Bradley·Terry 두 사람의 1952년 논문. 원래 문제는 "모든 팀이 다 붙어보진 않은 리그의 순위 매기기")

### 아이디어 한 줄

각 사진에 "실력" π를 하나씩 붙이고, **승률 = 내 실력의 점유율**이라고 가정한다.

```
P(P1이 P2보다 선택될 확률) = π₁ / (π₁ + π₂)
```

축구 승률처럼 생각하면 쉽다. 실력 7 vs 실력 2면 7/(7+2) = 78% 정도로 이긴다.

### σ 형태로 바꾸기

π는 항상 양수여야 해서 다루기 불편하다. `β = log π`로 놓으면 (거꾸로 `π = e^β`) 이렇게 된다.

```
P(i ≻ j) = e^{β_i} / (e^{β_i} + e^{β_j}) = σ(β_i − β_j)

  σ(z) = 1/(1+e^{−z})   ← 시그모이드. 실수를 0~1 확률로 짜부라뜨리는 함수
```

**"승률은 두 점수의 차이만으로 정해진다"** 는 뜻이다.

### 손계산 — P1 vs P2

```
β₁ = 2.0,  β₂ = 0.7          (앞의 표에서 u = w·x)

[π 형태]  π₁ = e^2.0 = 7.389
          π₂ = e^0.7 = 2.014
          7.389 / (7.389 + 2.014) = 7.389 / 9.403 = 0.786

[σ 형태]  σ(2.0 − 0.7) = σ(1.3) = 1 / (1 + e^{−1.3})
                                = 1 / (1 + 0.2725) = 1 / 1.2725 = 0.786   ← 같다 ✓
```

**즉 이 부부는 P1(웃는 클로즈업)과 P2(역광 실루엣)를 나란히 보여주면 약 79% 확률로 P1을 고른다.**
100%가 아니라는 게 중요하다. 사람은 기계가 아니라서 그날 기분에 따라 21%는 P2를 고른다.

### 점수차 → 확률 환산표 (외워둘 것)

| 점수 차 | 0 | 0.5 | 1 | 1.5 | 2 | 3 |
|---|---|---|---|---|---|---|
| 이길 확률 | 50.0% | 62.3% | 73.1% | 81.8% | 88.1% | 95.3% |

**차이 1 = 73%밖에 안 된다.** "웬만하면 이건데 뒤집힐 수 있다" 수준이지 압도가 아니다.
P1 vs P3(단체사진)은 차이가 3.0이라 95%다 — 이 정도가 되어야 "확실히 이 부부 취향"이라 말할 수 있다.

이 표는 나중에 실제로 쓰인다:
- 이유 문장의 강도 — 차이 3이면 "이건 확실히 취향이십니다", 차이 0.5면 "이것도 한번 보세요"
- λ(신뢰도) 임계값을 정할 때의 감각

### 절편(intercept)이 없는 이유 두 가지

`fit_intercept=False`가 코드에 있다. 취향이 아니라 **수학적 필연**이다.

**(1) 상수를 더해도 아무 일이 안 일어난다 (식별 불가)**

```
원래:      e^2.0 / (e^2.0 + e^0.7)     = 7.389/9.403  = 0.786
둘 다 +1:  e^3.0 / (e^3.0 + e^1.7)     = 20.09/25.56  = 0.786   ← 한 자도 안 변함
```

모든 사진의 점수를 통째로 +100 해도 확률이 똑같다. 그러니 "절대 높이"를 정하는 숫자(절편)는
데이터로 알아낼 방법이 원리적으로 없다. **차이만 의미가 있다.**

**(2) 쌍 비교는 반대칭이어야 한다**

`P(P1≻P2) + P(P2≻P1) = 1` 이어야 한다(둘 중 하나는 반드시 선택되니까).
절편 b를 넣으면 `σ(w·d + b)` 와 `1 − σ(−w·d + b) = σ(w·d − b)` 가 같아야 하는데,
그러려면 **b = 0** 밖에 답이 없다.

### 설계안 연결
- 온보딩을 별점이 아니라 쌍 비교로 하는 이유 (`plan.md` §3-B)
- `pair_comparison_events` 테이블이 `photo_a`, `photo_b`, `chosen` 구조인 이유

### 자가 점검
- σ(1.3)을 π 형태와 σ 형태 양쪽으로 계산할 수 있나?
- 모든 사진 점수에 +5를 하면 추천 순서가 바뀌나? → 안 바뀐다

## 2. 왜 β_i가 아니라 β_i = w·x_i 인가 — 일반화

### 장면

1절의 방식(사진마다 점수 하나)을 그대로 쓰면 이렇게 된다.

> 이 부부의 P1 점수 = 2.0, P2 점수 = 0.7, P3 점수 = −1.0 …

그럴듯하다. **그런데 다음 부부가 온다.** 그 부부의 갤러리는 다른 결혼식, 다른 사진 320장이다.
**겹치는 사진이 단 한 장도 없다.** 우리가 열심히 배운 "P1 = 2.0"은 그 부부에게 아무 의미가 없다.

심지어 같은 부부 안에서도 문제다. 온보딩 12쌍에 등장한 사진은 최대 24장. **나머지 296장은
점수를 매길 근거가 하나도 없다.** 추천할 수가 없다.

> **핵심 문제: "이 사진"에 점수를 붙이면 새 사진에 옮겨갈 수 없다.**

### 해결 — 사진의 "정체" 대신 "속성"에 점수를 붙인다

```
바꾸기 전:  β_i = (사진 i 전용 숫자)        ← 사진이 바뀌면 사라짐
바꾼 후:    β_i = w · x_i                   ← w는 태그에 붙으므로 사진이 바뀌어도 남음
```

"P1이 좋다"가 아니라 **"클로즈업이 +0.8, 웃음이 +1.2 좋다"** 를 배우는 것이다.
그러면 처음 보는 사진도 태그만 있으면 즉시 점수가 나온다. 이걸 **contextual BT** 라고 부른다.

| | 아이템별 BT (원형) | contextual BT (우리) |
|---|---|---|
| 배우는 것 | 사진 320개의 점수 | 태그 33개의 가중치 |
| 파라미터 수 | 사진 수만큼 (갤러리마다 다름) | 33개 (고정) |
| 새 사진 | **값이 없음** | 태그만 있으면 계산됨 |
| 새 갤러리 | **전부 값이 없음** | 그대로 씀 |

### 차이 벡터 d

두 식을 합치면 이렇게 된다.

```
P(i ≻ j) = σ(β_i − β_j) = σ(w·x_i − w·x_j) = σ(w · (x_i − x_j)) = σ(w · d)

  d = x_i − x_j   ← "차이 벡터"
```

**이 형태가 곧 절편 없는 로지스틱 회귀다.** BT loss를 따로 구현할 필요가 없다는 뜻이다
(4절에서 실제로 확인한다).

### 손계산 — 그리고 여기서 가장 중요한 발견

P1(웃는 클로즈업) vs P2(역광 실루엣, 웃음):

```
x_P1 = [1, 0, 1, 0, 0]
x_P2 = [0, 0, 1, 1, 0]
d    = [1, 0, 0, −1, 0]
        ↑        ↑
     closeup   backlit
        smile 자리가 0이 됐다!

w·d = 0.8·1 + (−0.5)·(−1) = 1.3   ← β₁ − β₂ 와 정확히 같음 ✓
```

> **`smile` 항이 사라졌다.** 둘 다 웃는 사진이니까.
> 이 쌍은 `smile` 가중치에 대해 **아무것도 가르쳐주지 않는다.** w의 smile이 +1.2든 −1.2든
> 이 쌍의 예측은 똑같다.

**규칙: 쌍이 가르쳐주는 것은 "두 사진이 다른 축"뿐이다.**

이건 온보딩 쌍 설계의 뿌리다. 만약 P1 vs P3(단체 와이드)를 물어보면:

```
d = [1, −1, 1, 0, −1]    ← 4개 축이 한꺼번에 다르다
```

부부가 P1을 골랐을 때 **왜 골랐는지 알 수가 없다.** 클로즈업이라서? 웃어서? 단체가 싫어서?
그래서 설계안의 온보딩 쌍 규칙은 **"같은 장면, 한 축만 다름, 품질 비슷"** 이다.
교란변수를 제거해서 한 쌍이 한 축만 가리키게 만드는 것.

**대가도 있다.** 같은 scene끼리만 비교하면 `d`의 scene 자리가 항상 0이 되므로,
**"이 부부가 반지 사진을 좋아하는가"는 원리적으로 학습되지 않는다.** (step2 주제)

### 실습에서 본 숫자 — 대조군 실험

`step1_bt.py`의 `[c]` 블록이 이걸 숫자로 보여준다. 사진마다 파라미터 하나(원핫 200차원)로 학습하면:

```
contextual BT : 0.733
아이템별 BT   : 0.633    (그중 처음 보는 사진이 낀 쌍 17/90개)
```

정확도도 지지만 진짜 결론은 그게 아니다. **처음 보는 사진이 낀 쌍은 예측 근거가 0**이고
(사실상 동전 던지기), 새 갤러리에서는 그 비율이 **100%** 다.

### 설계안 연결
- 왜 협업 필터링(CF/MF)을 안 쓰는가 — 갤러리마다 아이템 풀이 완전히 다르고, 콜드스타트가 예외가 아니라 기본 상태
- 온보딩 쌍 생성 규칙 (`plan.md` §3-B)

### 자가 점검
- 온보딩에서 "역광 웃는 반신" vs "자연광 진지한 클로즈업"을 물어봤다. 이 쌍이 가르쳐주는 축은?
  → framing, lighting, expression 세 개가 섞여 있어서 원인 분리 불가. 나쁜 쌍이다.

## 3. w는 어떻게 구하나 — NLL과 기울기

### 장면

부부가 온보딩 12쌍을 다 눌렀다. 이제 `w`(숫자 5개, 실제로는 33개)를 정해야 한다.
후보는 무한히 많다. `[0.8, −0.3, 1.2, −0.5, −0.7]`도 가능하고 `[3, 3, 3, 3, 3]`도 가능하다.

**어떤 w가 더 좋은지 재는 숫자가 필요하다.** 그게 없으면 "학습"이라는 말 자체가 성립 안 한다.

### 아이디어 — 최대우도

> **실제로 부부가 한 선택들에 가장 높은 확률을 부여하는 w를 고른다.**

부부가 12번 다 P1쪽을 골랐는데, 어떤 w가 "P1이 이길 확률 20%"라고 말한다면 그 w는 틀린 거다.

```
우도 L(w) = σ(w·d₁) × σ(w·d₂) × … × σ(w·d₁₂)
            └─ 1번 쌍에서 실제 선택이 일어날 확률
```

이걸 최대화하면 된다. 그런데 곱은 다루기 나쁘다:

| 문제 | 해결 |
|---|---|
| 확률 300개를 곱하면 `1e-90` 같은 수 → float가 0으로 만듦 (언더플로) | `log`를 씌우면 곱 → 합 |
| 곱의 미분은 복잡함 | 합의 미분은 항별로 따로 |
| 최적화 라이브러리는 최소화만 함 | 부호를 뒤집어 최소화 문제로 |

그래서 **음의 로그우도(Negative Log-Likelihood)**:

```
NLL(w) = − Σ_k log σ(w · d_k)
```

`d_k = x_chosen − x_rejected` 로 만들어 두면 모든 항이 `σ(w·d)` 형태라 식이 저렇게 단순해진다.

### NLL을 읽는 법 — 기준선은 0.693

w = 0(아무 취향 없음)이면 모든 예측이 50%다.

```
쌍당 NLL = −log(0.5) = 0.693
```

> **0.693 = 동전 던지기의 점수.** 쌍당 NLL이 이것보다 낮아야 뭔가 배운 것이다.
> `exp(−NLL/쌍수)` 를 계산하면 "실제 선택에 부여한 평균 확률"로 바로 읽힌다.

### 왜 정확도를 직접 최적화하면 안 되나

정확도가 더 직관적인데 왜 NLL을 쓸까? **정확도로는 학습이 불가능하기 때문**이다.

```python
return float((margin > 0).mean())     # ← 계단함수
```

`margin > 0`은 0 아니면 1로 툭 튄다. w를 아주 조금 움직여도 값이 안 변하다가 어느 순간 뚝 바뀐다.
→ **기울기가 거의 모든 곳에서 0.** "어느 쪽으로 가야 나아지는지"를 알려주지 못한다.

NLL은 반대다:
- **매끄럽다** — 기울기가 항상 있다
- **볼록(convex)하다** — 웅덩이가 하나뿐이라 **전역 최적해가 보장**된다.
  초기값·시드에 따라 결과가 달라지지 않는다. 그래서 `np.zeros`에서 출발해도 되고, 재실행이 멱등하다

### 정확도가 못 보는 것 — 캘리브레이션

정확도는 **순서만** 본다. 51% 확신으로 맞춘 것과 99% 확신으로 맞춘 것이 같은 점수다.
NLL은 확신 정도까지 채점한다. 홀드아웃 10쌍으로:

| 모델 | 정확도 | 쌍당 NLL | `exp(−NLL/K)` |
|---|---|---|---|
| A 확신형 (맞을 땐 95%, 틀릴 땐 5%) | 0.70 | **0.935** | 0.393 |
| B 신중형 (맞을 땐 60%, 틀릴 땐 40%) | 0.70 | **0.632** | 0.531 |
| 전부 50% (동전) | — | 0.693 | 0.500 |

정확도로는 동점인데 **A는 동전 던지기보다도 나쁘다.** 자신 있게 틀리기 때문이다.

우리 제품에서 이게 왜 치명적이냐면, AI 셀렉터는 **정답을 맞추는 기능이 아니라 설득하는 기능**이라
확신도가 그대로 화면에 나가기 때문이다:
- 이유 문장의 강도 ("확실히 취향이십니다" vs "이것도 한번 보세요")
- λ — 취향 증거가 약하면 사진학 prior로 넘기는 판단
- 후회율 — 강하게 추천했는데 안 담으면 신뢰가 무너진다

### 기울기 — 모델은 "지금 틀리는 쌍"에서만 배운다

```
∇NLL = − Σ_k (1 − σ(w·d_k)) · d_k
              └──────────┘
              이 쌍을 틀릴 확률
```

가중치가 **틀릴 확률**이다. 그래서:

| 상황 | (1−σ) | 결과 |
|---|---|---|
| 이미 잘 맞추는 쌍 (σ≈1) | ≈ 0 | **아무것도 안 가르친다** |
| 헷갈리는 쌍 (σ≈0.5) | 0.5 | 중간 정도로 당긴다 |
| 틀리는 쌍 (σ≈0) | ≈ 1 | **세게 당긴다** |

이게 온보딩 쌍 선택 전략(뻔한 쌍 말고 모델이 모르는 쌍을 물어봐야 한다 = active learning)과
👎 피드백이 강한 신호인 이유의 수학적 근거다.

### 손계산 — 경사하강 한 스텝

쌍 2개로 해보자.

```
쌍1: P1 ≻ P2   →  d₁ = [ 1,  0, 0, −1,  0]
쌍2: P1 ≻ P3   →  d₂ = [ 1, −1, 1,  0, −1]
```

**출발: w = [0,0,0,0,0]** (아무 취향 없음)

```
z₁ = w·d₁ = 0  →  σ = 0.5
z₂ = w·d₂ = 0  →  σ = 0.5
NLL = −log0.5 − log0.5 = 0.693 + 0.693 = 1.386      ← 쌍당 0.693, 딱 동전 던지기
```

**기울기:**

```
∇NLL = − [ (1−0.5)·d₁ + (1−0.5)·d₂ ]
     = − [ 0.5·[1,0,0,−1,0] + 0.5·[1,−1,1,0,−1] ]
     = − [1.0, −0.5, 0.5, −0.5, −0.5]
     = [−1.0, 0.5, −0.5, 0.5, 0.5]
```

**한 스텝 (학습률 1, `w ← w − ∇`):**

```
w = [1.0, −0.5, 0.5, −0.5, −0.5]
     closeup+  wide−  smile+  backlit−  group−
     ↑ 방향이 전부 맞다! (진짜 취향은 [0.8, −0.3, 1.2, −0.5, −0.7])
```

**확인:**

```
z₁ = 1.0·1 + (−0.5)·(−1) = 1.5   →  σ = 0.818
z₂ = 1.0 + 0.5 + 0.5 + 0 + 0.5 = 2.5  →  σ = 0.924
NLL = 0.201 + 0.079 = 0.280       ← 1.386에서 0.280으로. 배웠다 ✓
```

단 한 스텝 만에 쌍당 NLL이 0.693 → 0.140이 됐다.

### L2 정규화 — 옵션이 아니라 필수 안전장치

```
목적함수에  + ½·reg·‖w‖²   /   기울기에  + reg·w
```

**왜 이게 MAP인가.** 베이즈로 `posterior ∝ likelihood × prior`. 사전분포를 `w ~ N(0, τ²I)`로 두고
`−log`를 취하면 `‖w‖²/(2τ²)`가 나온다. 즉 **reg = 1/τ²**.
`reg = 1.0`은 "태그 하나의 가중치는 표준편차 1 정도, 즉 승산을 `e¹ ≈ 2.7`배쯤 움직이는 게 보통"이라는
사전 믿음이다. **"12쌍 봤다고 태그 하나에 8.0을 주지 마라"** 는 제동장치.

**없으면 실제로 터진다.** 쌍이 선형분리 가능하면(= 모든 쌍을 완벽히 맞추는 w가 존재하면)
w를 같은 방향으로 계속 키울수록 모든 σ가 1에 가까워져 NLL이 0으로 내려간다.
→ **최소점이 무한대에 있어서 MLE가 발산한다.**

우리는 **온보딩 12쌍 × 태그 33차원**이다. 미지수가 관측보다 많으니 거의 확실히 분리 가능하다.
정규화 없이 돌리면 "두 번 본 태그에 가중치 8.0" 같은 해가 나오고, 그 태그 달린 사진이
무조건 1위를 독식한다.

### 설계안 연결
- λ = f(증거량)과 같은 철학 — 증거가 적으면 결론을 약하게 (§3-B)
- 결정적(비-LLM) 계산이라 재실행 멱등 (§4)

### 자가 점검
- w=0에서 쌍당 NLL은? → 0.693
- 홀드아웃 쌍당 NLL이 0.71이 나왔다. 이 모델은 쓸 만한가? → 동전보다 나쁘다. 못 쓴다
- 온보딩 12쌍 33차원에서 L2를 빼면? → 발산. 특정 태그가 순위를 독식

## 4. sklearn으로 바꾸는 법 — 부호 대칭 증강

### 장면

2절에서 `P(i≻j) = σ(w·d)` 가 **절편 없는 로지스틱 회귀와 완전히 같은 식**임을 봤다.
그러면 BT 코드를 직접 짤 필요 없이 `LogisticRegression`을 쓰면 된다. 그런데 막상 넣으면 터진다.

```python
ValueError: This solver needs samples of at least 2 classes
```

**이유:** 우리는 `d = chosen − rejected` 로 만들었으니 정답이 **전부 y=1** 이다.
분류기 입장에서는 "전부 정답"인 데이터라 학습할 게 없다.

### 해결 — 각 쌍을 두 줄로 넣는다

```
(  d, y=1 )   "P1이 P2보다 낫다"
( −d, y=0 )   "P2가 P1보다 낫지 않다"     ← 같은 말을 뒤집은 것
```

당연히 같은 사실인데, 수식으로도 정확히 같은 항이다:

```
log σ(w·d) = log(1 − σ(−w·d))

확인:  σ(1.3) = 0.786
       σ(−1.3) = 0.214  →  1 − 0.214 = 0.786   ✓ 같다
```

부수 효과로 데이터가 원점 대칭이 되어, **절편을 켜 두더라도 0으로 추정된다** (1절의 반대칭과 일관).

### 함정 — 손실이 두 번 세어진다

같은 쌍이 두 줄이 됐으니 로그우도 항이 **2배**가 된다. 정규화 세기가 상대적으로 절반이 되는 셈이다.
sklearn의 `C`는 **정규화의 역수**라 보정이 필요하다.

```
우리 목적함수     :        Σ logloss + ½·reg·‖w‖²
sklearn 목적함수  : C · (2·Σ logloss) + ½·‖w‖²

sklearn 쪽을 2C로 나누면:  Σ logloss + (1/4C)·‖w‖²
같아지려면  1/(4C) = ½·reg   →   C = 1/(2·reg)
```

그래서 코드가 이렇다:

```python
clf = LogisticRegression(fit_intercept=False, C=1.0/(2*reg), tol=1e-10, max_iter=5000)
```

### 실습에서 본 숫자 — 동등성 증명

```
w_true    : [ 1.   −0.5   0.3   0.    0.8 ]
BT (직접) : [ 0.93 −0.484 0.382 −0.103 0.944]
LogReg    : [ 0.93 −0.484 0.382 −0.103 0.944]
두 해의 최대 절대 차이: 2.57e-06
```

**소수점 6자리까지 같다.** BT loss를 따로 구현할 필요가 없다는 것의 증거.
(실전에서는 직접 구현 대신 sklearn을 쓰면 되고, 코드 한 뭉치와 버그 가능성이 사라진다.)

### 자가 점검
- 증강 없이 넣으면 왜 에러인가? → 클래스가 하나뿐
- `C = 1/(2·reg)`의 2는 어디서 왔나? → 증강으로 손실 항이 2배가 돼서

## 5. 그 숫자를 어떻게 읽나 — 정답이 없는 문제의 채점

### 장면

`w`를 배웠다. 잘 배운 걸까? **누가 채점하지?**

여기서 이 프로젝트의 가장 중요한 설계 결정이 나온다.

### "정답 셋"은 두 가지 뜻이고, 하나만 필요하다

**(a) 객관적 정답 — "이 사진이 뽑혔어야 할 사진"**
→ **없다. 만들지 않는다.**

`plan.md` §6: *"정답 라벨은 없다. 작가마다·고객마다 좋은 사진이 다르다."*
실제로 08-22 멘토 미팅 후 기존 골든셋의 `selected` 이진 라벨과 AUC/recall@K를 **폐기**했다
(`spike-report.md`). `../dataset`은 이제 사진 소스로만 쓰고 라벨링은 하지 않는다.

**(b) 그 사람이 실제로 한 선택 기록**
→ **필요하고, 이미 있다.**

이건 우리가 정해주는 정답이 아니다. 부부가 A를 골랐다는 사실은 **그 부부에게는 정의상 옳다.**
반박할 사람이 없다.

여기가 이 문제의 좋은 점이다. **채점표를 사용자가 스스로 만들어 준다.**

```
12쌍을 받는다  →  9쌍으로 학습  →  나머지 3쌍은 숨겨뒀다가 맞추는지 본다
```

라벨링 비용 0. 전문가 섭외 불필요. 사진이 몇 장이든 무관.

| | 전형적 지도학습 | 우리 |
|---|---|---|
| 라벨 출처 | 전문가가 붙임 | 사용자의 선택 행동 그 자체 |
| 라벨의 권위 | 합의된 정답 | 그 사용자에게만 옳음 (개인화 모델이니 충분) |
| 비용 | 사진 수 비례 | 사람당 12쌍, 온보딩 중 자동 발생 |
| 실패 모드 | 라벨러 편향 | **사람이 확률적** → 라벨 노이즈 |

### 바닥과 천장 — 정확도는 절대 수치로 읽으면 안 된다

```
[홀드아웃] 쌍 예측 정확도 0.733  (66/90)
  95% CI [0.634, 0.814]   p(우연 50% 대비) = 0.0000
  참고: 정답 w_true를 그대로 써도 0.744  ← 도달 가능한 천장
```

**바닥 0.5** — 동전 던지기. 이보다 나아야 의미가 있다.

**천장 0.744** — **정답 w를 알아도 100%가 안 나온다.** 왜?
1절에서 봤듯 점수 차 0.3짜리 쌍은 정답을 알아도 43% 확률로 "지는" 쪽이 선택된다.
**사람이 확률적으로 고르기 때문에 라벨 자체에 노이즈가 있다.**

그래서 0.733은 "73%밖에 못 맞춤"이 아니라 **"천장의 98.5%"** 로 읽어야 한다.

**주의: `w_true`는 합성 세계에만 있다.** 실전에는 이 줄이 없다.
그래서 실전 판정은 천장 대비가 아니라 **바닥(0.5) 대비 + 신뢰구간**으로 한다.

### Wilson CI와 이항검정 — "그 숫자를 믿어도 되나"

정확도 하나만 보면 안 된다. 표본이 작으면 우연히 나온 숫자일 수 있다.

```
90쌍에서 66/90 = 73.3%  →  95% CI [0.634, 0.814]   폭이 ±9%p
```

**90쌍이나 있어도 0.70과 0.75를 구분 못 한다.** 이게 실험 설계에 직접 영향을 준다.

실전 시나리오로 계산해 보자. **사람 8명 × 홀드아웃 3쌍 = 24표본:**

| 결과 | 정확도 | 95% CI | p값 | 판정 |
|---|---|---|---|---|
| 15/24 | 62.5% | [0.427, 0.788] | 0.154 | **아직 아무 말도 못 한다** (CI가 0.5를 포함) |
| 18/24 | 75.0% | [0.551, 0.880] | 0.011 | 우연보다 낫다고 말할 수 있다 |

**필요 표본 수** (`required_pairs`, 유의수준 5%·검정력 80%):

| 진짜 정확도가 이 정도라면 | 우연과 구분하는 데 필요한 홀드아웃 쌍 |
|---|---|
| 0.70 | 37쌍 |
| 0.65 | 67쌍 |
| 0.60 | **153쌍** |

**차이의 제곱에 반비례한다.** 효과가 작을수록 표본이 급격히 많이 필요하다.
사람당 3쌍이면 0.65를 증명하는 데 **23명**이 필요하다는 뜻. W1–2 실험 설계의 근거가 이것이다.

### 실습에서 본 숫자 — 쌍이 몇 개 필요한가

```
학습쌍 | 홀드아웃 정확도
     8 | 0.689
    12 | 0.589
    25 | 0.700
    50 | 0.678
   100 | 0.756
   209 | 0.733
```

**단조 증가가 아니다.** 12쌍이 8쌍보다 나쁘게 나왔다. 이것도 노이즈다 —
홀드아웃 90쌍의 CI가 ±9%p니까 0.589와 0.689의 차이는 **구분 가능한 차이가 아니다.**
"12쌍이 8쌍보다 나쁘다"고 결론 내리면 오독이다.

### 쌍 정확도가 못 보는 것

주지표이긴 하지만 이것만으로는 부족하다. 쌍 정확도는 **두 장 중 위아래**만 본다:

| 실패 | 쌍 정확도로 잡히나 | 잡는 지표 |
|---|---|---|
| 추천 30장이 전부 신부 클로즈업 | ❌ | 장면 커버리지 (step4) |
| 같은 연사 5장이 다 상위에 | ❌ | 클러스터 중복 제거 (step4) |
| 상위 5장은 좋은데 6~30위가 엉망 | ❌ (쌍은 순위 위치를 모름) | nDCG (step5) |
| 강하게 추천했는데 안 담음 | ❌ | 수락률·후회율 (step5) |

## 6. 이 `w`는 실제 추천 어디에 들어가는가 — 사진학과의 관계

### 장면

부부가 갤러리를 열자마자 온보딩도 안 하고 **"AI 추천"을 눌렀다.** 쌍 비교 0개, 별점 0개.
`w`가 없다. 그럼 아무것도 추천 못 하나?

추천한다. **취향을 모를 때 대신 답해주는 것이 사진학 prior** 다.

### 전체 점수식 (`plan.md` §3-B)

```
score(p) = (1−λ)·prior(p) + λ·pref(p) + coverage_bonus(p) − mmr_penalty(p)
           └── 사진학 ──┘   └─ 취향 ─┘   └──── 목록 만들기 단계 (step4) ────┘

prior(p) = technical_pct·w_t + aesthetic_pct·w_a      # ARNIQA + LAION, 갤러리 내 백분위
pref(p)  = Σ_axis conf(axis)·P(tag_axis(p) | 선호분포) + β·max_sim(p, 선호벡터)
λ        = f(evidence 수)                              # 증거가 쌓일수록 커짐, 상한 있음
```

**STEP 1에서 배운 `w`는 `pref` 안에 있다.** 0절의 `④ 점수 매기기`에서 `u = w·x`라고 단순화했던
그 자리가, 실제로는 이 식이다.

### ① 순차가 아니라 저울이다

흔한 오해: *"사진학으로 먼저 추천하고, 나중에 취향을 더한다."* 아니다.
**처음부터 둘을 섞되, λ가 evidence 개수에 따라 움직여서 무게중심이 옮겨간다.**

| 시점 | evidence | λ | 실질 |
|---|---|---|---|
| "AI 추천" 첫 클릭 | 0개 | **~0.2** | 사진학 80% — 사실상 "잘 찍힌 사진 순" |
| 온보딩 12쌍 직후 | 12 | 중간 | 절반씩 |
| 12쌍 + 별점 20개 | 32 | **~0.7** | 취향 70% — 사진학은 배경으로 물러남 |

**사진학이 사라지지는 않는다.** λ에 상한을 둬서 1에 못 간다. 증거가 아무리 많아도 흔들리고
눈 감은 사진이 최상단에 오르는 걸 막는 바닥 역할을 계속한다.

### 손계산 — 같은 사진, 같은 갤러리, 순서가 뒤집힌다

| | 기술/미학 백분위 | prior | 이 부부 취향 pref |
|---|---|---|---|
| **Q1** 하객 단체 와이드, 아주 잘 찍힘 | 92 / 88 | 0.90 | 0.15 |
| **Q2** 신부 클로즈업 웃음, 평범한 화질 | 55 / 60 | 0.575 | 0.90 |

```
λ = 0.2 (온보딩 전)
  Q1 = 0.8·0.90  + 0.2·0.15 = 0.720 + 0.030 = 0.750   ← Q1이 위
  Q2 = 0.8·0.575 + 0.2·0.90 = 0.460 + 0.180 = 0.640

λ = 0.7 (12쌍 + 별점 20개)
  Q1 = 0.3·0.90  + 0.7·0.15 = 0.270 + 0.105 = 0.375
  Q2 = 0.3·0.575 + 0.7·0.90 = 0.173 + 0.630 = 0.803   ← 역전
```

**λ 하나가 바뀌었을 뿐인데 순서가 뒤집힌다.** 이게 λ의 전부다.
부부 입장에서는 "처음엔 무난한 사진을 보여주더니, 몇 번 골라주니까 내 취향을 알아듣더라"가 된다.

### ② 사진학 prior는 "좋은 사진 판별기"가 아니다

여기가 가장 오해하기 쉬운 곳이다. prior는 백분위 숫자 **두 개**뿐이다.

| 모델 | 산출 | 아는 것 |
|---|---|---|
| **ARNIQA** | `technical_pct` | 왜곡·블러·노이즈 = **기술 품질**. "잘 찍혔나" |
| **LAION Aesthetic v2** | `aesthetic_pct` | **대중 평균의 미학 점수** |

둘 다 **"웨딩 사진으로 좋은가"를 아는 모델이 아니다.** 구도가 이 결혼식에 어울리는지,
이 순간이 이 부부에게 의미 있는지는 전혀 모른다. 그래서 `plan.md`가 못박는다:

> **"경량 3종은 추천 점수의 주축이 아니다."** (08-19판보다 역할을 줄인 것)

그리고 CLAUDE.md의 강한 제약이 하나 있다:

> **품질 점수로 하드 필터링 금지.**

흔들린 사진이 그 부부에게는 최애일 수 있기 때문이다(부케 받는 순간, 아버지가 우는 컷).
prior는 낮은 **점수**를 줄 뿐, 후보에서 **빼지 않는다**.

**경량 3종이 실제로 쓰이는 곳은 세 군데인데, 추천 점수는 그중 하나뿐이다:**

| 용도 | 하는 일 |
|---|---|
| ① 사진학 prior | 취향을 모를 때의 기본선 |
| ② 클러스터 대표 선정 | 연사 5장 중 눈 감고 흔들린 것 피하기 |
| ③ **온보딩 쌍의 품질 근접 조건** | "둘 다 괜찮은데 어느 스타일?"이 되게 |

③이 STEP 1과 직결된다. 화질이 다른 두 장을 비교시키면 부부는 스타일이 아니라 **화질**을 고르고,
그러면 우리는 취향이 아니라 화질을 학습하게 된다. 2절에서 본 "쌍은 다른 축만 가르친다"의
연장선 — **사진학이 취향 학습의 교란변수를 제거하는 데 쓰인다.**

### ③ STEP 1의 `w`는 `pref`의 일부다

실제 `pref`는 STEP 1보다 두 겹 더 있다.

```
pref(p) = Σ_axis conf(axis)·P(tag_axis(p) | 선호분포)  +  β·max_sim(p, 선호벡터)
          └────── 축별 태그 선호 (STEP 1의 w) ──────┘     └─ DINOv2 임베딩 유사도 ─┘
                     ↑
              conf(axis): 그 축의 선호가 50:50에 가까우면 0
```

- **`conf(axis)`** — λ가 **전역** 축소라면 이건 **축별 차등** 축소다.
  12쌍 중 framing은 6쌍이 물었지만 lighting은 1쌍뿐이라면, lighting 가중치는 거의 무시한다.
  *"애매한 축은 자동으로 사진학 우선."* (3절의 L2와 같은 철학 — 증거가 적으면 결론을 약하게)
- **임베딩 유사도** — 태그 33개로 안 잡히는 미세 취향("같은 클로즈업이라도 이런 톤")을 재정렬로 잡는다.

**그리고 취향 신호는 쌍 비교만이 아니다.**

| 신호 | 비고 |
|---|---|
| 별점 1~5 (`photo_ratings`) | **정보량이 가장 크다. 있으면 주 신호** |
| 수동 선택 (`photo_selection_items`) | 읽기 전용 |
| **쌍 비교** (`pair_comparison_events`) | 별점·선택이 부족할 때만 = **콜드스타트 수단** |
| 👍/👎·수락/거절 | 2차 셀렉의 입력이자 지표 |
| 자연어 | LLM이 `{axis, tag, delta}`로 번역 |

STEP 1이 쌍 비교로 시작하는 건 그게 **가장 어려운 경우**(아무 정보도 없는 상태)이기 때문이다.

### ④ 점수 순 정렬이 최종이 아니다

```
점수 정렬 → 장면 커버리지(장면마다 최소 장수) → 클러스터당 1장 → MMR(비슷한 것 감점)
```

점수만 쓰면 상위 30장이 전부 "신부 클로즈업 웃음"이 된다. **취향에는 100% 맞지만 앨범이 안 된다.**
그래서 커버리지와 MMR이 뒤에 붙는다 (step4).

### 한 줄 정리

> **사진학 prior와 취향을 λ로 저울질해 섞고, 축별로 conf를 곱해 증거 없는 축은 죽이고,
> 그 점수를 커버리지와 MMR로 재배열한다. λ와 conf가 증거량에 따라 자동으로 움직이므로,
> 아무것도 모를 땐 사진학이 답하고 알게 될수록 취향이 답한다.**

사진학은 주인공이 아니라 **취향이 말할 수 있을 때까지 자리를 지키는 대역**이다.
CLAUDE.md의 한 줄이 이걸 요약한다 — *"취향 증거가 적거나 애매하면 자동으로 사진학이 우선."*

### 자가 점검
- λ=0.2와 λ=0.7에서 Q1·Q2의 순서가 왜 뒤집히나? 손으로 계산할 수 있나?
- ARNIQA 점수가 하위 5%인 사진은 추천에서 제외되나? → **아니다. 하드 필터링 금지**
- 온보딩 쌍을 만들 때 품질이 비슷한 것끼리 묶는 이유는? → 안 그러면 스타일이 아니라 화질을 학습

## 7. 남은 질문 → step2

STEP 1의 마지막 표가 이렇게 끝났다.

```
학습쌍 8개 → 홀드아웃 정확도 0.689     (5차원)
```

**5차원이라서** 8쌍으로도 됐다. 그런데 실제 태그는 **33차원**이고, 임베딩은 **768차원**이다.
온보딩은 여전히 12쌍이다.

2절에서 본 성질을 떠올리면 왜 이게 무서운지 알 수 있다:

> **쌍이 가르쳐주는 것은 두 사진이 다른 축뿐이다.**

12쌍이면 아무리 잘해야 **12개 축**에 대한 정보밖에 없다. 33개 중 나머지 21개는
**단 한 번도 관측되지 않는다.** 768차원이면 말할 것도 없다.

그러면 이런 일이 벌어진다:
- 한 번 나온 태그에 큰 가중치가 붙고 그 태그 사진이 순위를 독식한다 (3절의 발산 문제)
- 관측 안 된 축은 w = 0 근처인데, 그게 "관심 없다"인지 "모른다"인지 구분이 안 된다

**여기서 설계안의 나머지 조각들이 왜 필요한지가 나온다:**

| 장치 | 푸는 문제 | 실습 |
|---|---|---|
| **사진학 prior** | 취향 증거가 없을 때 기댈 기본 점수 | step3 |
| **λ = f(증거량)** | 증거가 적으면 취향 가중을 통째로 줄인다 | step3 |
| **conf(axis)** | 축마다 관측량이 다르니 축별로 차등 축소 | step3 |
| **커버리지·MMR** | 순위 독식·다양성 붕괴 | step4 |

> STEP 1의 결론은 "쌍 비교로 취향을 배울 수 있다"이고,
> STEP 2의 질문은 **"그런데 12쌍으로 33차원을 배울 수 있나?"** 다.

## 부록 — STEP 1 한 장 요약

| 절 | 질문 | 답 |
|---|---|---|
| 0 | STEP 1은 뭘 만드나 | `w` 하나. 이미지 처리(배치 A)도, 목록 생성(step4)도 아님 |
| 1 | 왜 쌍 비교인가 | 별점은 기준이 흔들림. BT가 상대 판정 → 절대 점수를 복원 |
| 1 | 왜 절편이 없나 | 상수 이동 불변(식별 불가) + 반대칭 요구 |
| 2 | 왜 `w·x`인가 | 갤러리마다 사진 100% 교체. 사진 이름표는 옮겨갈 수 없음 |
| 2 | 쌍이 가르치는 것 | 두 사진이 **다른 축**만. 같은 축은 d에서 0이 됨 |
| 3 | 왜 NLL인가 | 정확도는 계단함수라 최적화 불가. NLL은 매끄럽고 볼록 |
| 3 | 기울기의 의미 | 가중치 = 틀릴 확률. 지금 틀리는 쌍에서만 배움 |
| 3 | 왜 L2인가 | 12쌍 × 33차원은 선형분리 → 없으면 MLE 발산 |
| 4 | 왜 증강인가 | y가 전부 1이면 sklearn이 학습 거부. `C=1/(2reg)`로 보정 |
| 5 | 정답 셋이 필요한가 | 객관적 정답은 없음. 사용자 본인의 선택 기록이 채점표 |
| 5 | 정확도를 읽는 법 | 바닥 0.5 / 천장 <100% / CI 폭 확인 |
| 6 | w는 어디에 쓰이나 | `(1−λ)·사진학 + λ·취향` 의 취향 자리 |
| 6 | 사진학의 역할 | 주축이 아님. 취향을 모를 때의 대역 + 쌍 설계의 교란변수 제거 |
| 6 | 품질 낮은 사진은? | **제외하지 않는다.** 하드 필터링 금지 |

**외워둘 숫자 5개**

```
0.693  = 동전 던지기의 쌍당 NLL (= log 2)
0.5    = 쌍 정확도의 바닥
0.786  = σ(1.3), 점수차 1.3의 승률
73%    = 점수차 1의 승률 (생각보다 낮다)
±9%p   = 90쌍 홀드아웃의 95% CI 폭
```
