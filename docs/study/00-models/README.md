# 00-models — 우리가 쓰는 모델들

**여기가 첫 번째 영역이다.** 01(추천 로직)도 02(평가)도 "모델이 뱉은 숫자"를 다루는데,
그 숫자가 어디서 오는지 모르면 나머지가 전부 공중에 뜬다.

## 이 영역이 답하는 질문

```
① 모델이란 결국 무엇인가                    → lab/step1
② 우리는 어떤 모델을 쓰고, 각각 뭘 하나        → catalog.md
③ 그 모델은 무엇에 반응하고 어디서 못 믿나      → lab/step2
```

**이론이 거의 없다.** 실제 사진에 실제 모델을 돌려 보는 것이 전부다.
수식은 01·02에서 나온다.

## 파일

| 파일 | 역할 |
|---|---|
| `catalog.md` | **이 영역의 본체.** 다섯 모델의 카드 — 무엇을 하나 / 무엇을 학습했나 / 왜 골랐나 / 확인할 것 |
| `materials.md` | 각 모델을 더 읽을 자료 |
| `lab/harness.py` | 스파이크 하네스의 러너를 학습용으로 빌려 오는 어댑터 |
| `lab/step1_open_the_box.py` | 모델을 만져 본다 — 파일 크기·로딩 시간·입출력·속도 |
| `lab/step2_what_it_reacts_to.py` | 사진을 망가뜨려 가며 무엇에 반응하는지 본다 |

## 실행 — venv가 다르다

이 영역의 lab은 **`study/.venv`가 아니라 스파이크 venv**로 돌린다.
torch·mediapipe·open_clip이 거기 설치돼 있기 때문이다.

```bash
cd study/00-models/lab
../../../photoselect/scripts/spike/.venv/bin/python step1_open_the_box.py
../../../photoselect/scripts/spike/.venv/bin/python step2_what_it_reacts_to.py
```

첫 실행은 가중치를 받느라 몇 분 걸릴 수 있다(ARNIQA는 `torch.hub`, CLIP은 890MB).
두 번째부터는 캐시라 빠르다. 인터넷이 필요하다.

> 매니페스트가 없다는 오류가 나면 먼저:
> ```bash
> cd photoselect/scripts/spike
> .venv/bin/python manifest.py build --root ../../../../dataset --out out/manifest.csv
> ```

## STEP 1 — 상자를 열어 본다

**목적** — "모델"이라는 말이 추상적으로 들리는 동안에는 아무것도 안 남는다. 만져 본다.

**출력에서 볼 것**
- **모델은 파일이다.** MediaPipe 3.8MB, ARNIQA 107MB, CLIP 890MB. 크기가 곧 원가다
- **로딩이 추론보다 비싸다.** 3초 걸려 올리고 사진 한 장은 0.1~0.4초
  → A 배치가 갤러리당 1회로 도는 이유
- **세 모델이 같은 사진을 보고 다른 것을 말한다**
- 사진당 처리 시간 → `plan.md`의 '10분/1,000장' 예산과 직접 비교

**자가 점검**
1. 로딩 3초, 추론 0.2초일 때 사진 10장짜리 요청과 1,000장짜리 요청의 원가 구조가 어떻게 다른가?
2. 세 모델의 출력을 하나로 합치려면 무엇이 문제인가? (힌트: 단위)
3. `eyes_open`이 `nan`으로 나오는 사진은 어떤 사진인가?

## STEP 2 — 흔들어 본다 (이 영역에서 가장 중요한 실습)

**목적** — 논문을 읽지 않고도 "이 모델이 무엇에 반응하는가"를 알아내는 법.
사진 한 장을 흐리게·어둡게·흑백으로·크롭해 가며 점수 변화를 본다.

**핵심 장치 — 좌우 반전**
반전은 사진의 **내용을 하나도 안 바꾼다.** 그런데도 점수가 조금은 움직인다.
그 움직임이 **잡음의 바닥**이고, 다른 모든 변화를 그 바닥과 비교해서 읽는다.

> 02 영역이 "기준선 없는 숫자는 읽을 수 없다"고 계속 말한 것의 가장 단순한 형태다.
> 수식이 하나도 없이 같은 교훈에 도달한다.

**출력에서 볼 것**
- **`eyes_open`의 잡음 바닥이 0.629다.** 좌우 반전만 했는데 0.809 → 0.180
  → 그 열의 '잡음 수준' 판정은 "반응 안 한다"가 아니라 **"알 수 없다"** 는 뜻
- ARNIQA는 '많이 흐리게'에 29배 반응 (기술 품질 모델답다). '살짝 흐리게'는 1.9배로 애매
- 흑백으로 만들면 **ARNIQA는 내려가고 LAION은 올라간다** — 품질과 취향은 다른 축
- **[4] 반전 테스트를 12장에** — 라벨 0장으로 신호 안정성을 진단하는 법

**자가 점검**
1. 좌우 반전을 기준선으로 삼는 것이 왜 정당한가?
2. '해상도 1/4로'가 잡음 수준으로 나왔다. 그럼 해상도는 신경 안 써도 되나?
3. `eyes_open`이 반전에 흔들리는 사진들의 공통점은 무엇인가?

**변형 과제**
1. `variants()`에 JPEG 저품질 저장(`quality=20`)을 추가하라. ARNIQA가 압축에 반응하는가?
2. `sample_photos(..., seed=?)`를 바꿔 다른 사진으로 [1]을 다시 돌려라.
   `eyes_open`의 잡음 바닥이 사진마다 얼마나 다른가?
3. [4]의 표본을 30장으로 늘려라. 얼굴 크기와 반전 불안정성에 관계가 보이는가?

## 이 실습이 설계안에 되먹인 것

- **`eyes_open` 신뢰도는 라벨 없이 먼저 진단할 수 있다.** 좌우 반전은 정답을 안 바꾸므로
  반전 전후 차이가 곧 잡음의 크기다. 12장 중 3장이 0.3 넘게 흔들렸다.
  **스파이크 리포트의 '작은 얼굴 blink 신뢰도' 항목에 반전 테스트를 라벨링보다 먼저** 넣는다
- **흔들리는 쪽은 `eyes_open`이 높게 나온 사진들이다.** 낮은 값은 반전해도 안정적이다 —
  스파이크 리포트가 걱정한 방향("0.2대가 진짜 눈감김인가")과 반대다. 표본이 작아 결론은 보류
- **ARNIQA는 미세한 흐림을 못 잡는다.** '살짝 흐리게'가 잡음 바닥의 1.9배에 그친다.
  "흐린 사진을 걸러 준다"고 기대하면 안 되고, **심한 흐림만** 잡힌다
- **미리보기 해상도 고정(1600px)은 선택이 아니라 필수다.** 해상도가 바뀌면 점수가 바뀌므로
  사진마다 다른 크기로 넣으면 갤러리 내 백분위가 깨진다
