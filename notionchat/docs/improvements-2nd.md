# 2차 개선 — 검색 품질·평가 체계·가드레일 (2026-08-19)

> 1차가 "동작하는 챗봇"이었다면, 2차의 주제는 **"의도대로 답하는 챗봇"**이다.
> 핵심 교훈 하나로 요약된다: **측정 없이 개선 없다.** 오답을 발견할 때마다
> ① 원인을 층별로 진단하고 ② 고치고 ③ 그 사례를 골든 셋에 박아 재발을 감시한다.

## 전체 그림 — 무엇이 달라졌나

```
[1차]  질문 → 키워드 검색(search_notion) → 페이지 읽기 → 답변
[2차]  질문(+오늘 날짜 주입)
         → 워크스페이스 구조 지도(시스템 프롬프트)로 어디를 볼지 판단
         → 도구 6종: 팀 Notion 4종 + 스냅샷 2종(활동비 규정 / 소마 공식 일정)
         → 답변 (출처 정확성·복수 항목·시간 비교 규칙 적용)
       + 골든 셋 17문항으로 상시 회귀 검증
       + 조회 전용 가드레일 (코드 레벨 차단)
```

---

## 1. 검색 품질 — 4겹의 개선

### 1-a. 워크스페이스 구조 지도 (`api/core/workspace_map.md`)

> 개념: 모델이 매번 맨땅 검색하는 대신, **"어떤 질문이면 어디를 봐야 하는지"를 사람이
> 지도로 알려준다.** 실제 Notion 루트의 섹션 구조(Pages/References/Schedule…)를 따르고,
> 각 항목에 page_id를 적어 모델이 검색 없이 read_page로 직행할 수 있게 했다.

- 마크다운 파일 하나로 관리 — `prompts.py`가 서버 시작 시 읽어 시스템 프롬프트에 삽입.
  내용만 고치면 되고 코드는 안 건드린다. 안정 프리픽스라 **프롬프트 캐시에 실려**
  매 호출 추가 비용이 거의 없다.
- 갱신 도구: `python scripts/list_notion_ids.py` — 연결된 문서 전체의 id 목록을 덤프.
- 실전 교훈: 지도의 한 줄이 답변 품질을 좌우한다. "스튜디오 인터뷰" 항목을
  "인터뷰 기록"이라고 적었더니 모델이 질문 **템플릿** 페이지를 답했다 → 실제 녹취가 있는
  "인터뷰 결과 정리" 페이지와 구분해 적자 read_page 1회로 직행하게 됐다.

### 1-b. 오늘 날짜 주입 (`provider.py`)

> 문제: 시스템 프롬프트는 캐시 보호로 날짜를 못 넣는다 → 모델이 오늘이 언제인지 모른다
> → "다음 신청일", "지난주 회의" 같은 시간 상대 질문이 통째로 부정확했다.

```python
# run_turn에서 질문 앞에 붙인다 — 캐시 프리픽스 비오염 위치
now = datetime.now(ZoneInfo("Asia/Seoul"))   # Vercel은 UTC라 KST 명시
history.append({... f"[오늘: {now:%Y-%m-%d}({요일})] {question}" ...})
```

- 평가용으로 `run_turn(..., today="2026-08-19(수)")` 날짜 고정 파라미터도 추가 —
  시간 상대 골든 문항의 정답이 날짜가 지나도 안 변한다.
- 여기에 답변 규칙 추가: "종료일이 오늘 이전인 기간은 지난 것 — '다음'으로 답하지 않는다",
  "복수 항목 질문(활동비 + 학습비)은 항목마다 근거를 찾아 빠짐없이 답한다".

### 1-c. 외부 문서 스냅샷 — 새 도구 2종

> 문제: 자주 묻는 정보(활동비 규정, 소마 공식 일정, 자기주도 학습비)가 팀 Notion 밖에 있거나
> **이미지로만** 존재해서 모델이 볼 수 없었다.

| 도구 | 내용 | 원본 | 갱신 방법 |
|---|---|---|---|
| `read_expense_guide` | 활동비 규정 전문(차수별 신청 일정, 항목별 한도, 절차, 증빙) + 자기주도 학습비 안내 | 공개 노션(asm-busan.notion.site) + 로그인 공지 | `scripts/snapshot_asm_expenses.py` 재실행 / 학습비는 수동 |
| `read_soma_schedule` | 소마 공식 연수 일정(발대식·수료식·중간점검·TOPCIT·최종점검·교육·창업) | 팀 Notion 루트의 이미지 3장 | 이미지 갱신 시 수동 재변환 |

만드는 과정에서 배운 것들:

- **공개 notion.site는 비공식 API로 읽힌다** — 공식 API 토큰은 다른 워크스페이스라 404지만,
  게시 페이지 전용 엔드포인트(loadCachedPageChunkV2/queryCollection)는 인증 없이 동작.
  본문 + 내장 DB(행마다 본문 페이지까지)를 마크다운으로 변환했다. 비공식이라 깨질 수 있지만,
  런타임은 저장된 마크다운만 읽으므로 **서비스는 영향받지 않고 갱신만 못 하게 된다**.
- **이미지 표는 사람이(=Claude가) 읽어 옮긴다** — 신청 일정표·지원 항목 한도·소마 일정이
  전부 이미지였다. 표로 변환해 스냅샷에 병합. 파일마다 출처 URL·스냅샷 날짜를 박아
  모델이 답변에 신선도를 밝힐 수 있게 했다.
- **날짜는 ISO 형식으로** — "8/10(월)" 표기는 주입된 `[오늘: 2026-08-19]`와 형식이 달라
  모델이 비교를 흘렸다(지난 교육을 "진행 중"으로 오판). 시간순 단발성 일정 요약을
  `2026-09-18` 형식으로 추가하자 비교가 안정됐다.

### 1-d. 라우팅 명확화 — 비슷한 질문을 올바른 소스로

> 문제: "일정"·"비용"이라는 단어 하나에 소스가 셋씩 있다. 모델이 확률적으로 엉뚱한 데를 봤다.

경계를 도구 설명·지도·프롬프트 세 곳에 명시했다:

| 질문 | 올바른 소스 |
|---|---|
| "다음 활동비/학습비 신청일" | read_expense_guide (공식 규정) |
| "다음 멘토링 언제야" (팀 약속) | ASM 부산 17 일정 DB |
| "제일 가까운 **공식** 일정" | read_soma_schedule 단독 근거 |
| "우리 팀이 실제 쓴 비용" | Notion 비용 처리 DB |

- 출처 링크도 같은 원리로 교정: 학습비 답변에 활동비 규정 링크를 붙이던 문제 →
  각 스냅샷에 자기 출처 URL 명시 + "근거로 쓴 바로 그 문서의 출처를 쓴다" 규칙.

## 2. 골든 셋 평가 체계 (`tests/eval_questions.jsonl` + `tests/run_eval.py`)

> 개념: **검증된 문답을 회귀 테스트로 축적한다.** LLM 답변은 확률적이라 "한 번 고쳤다"가
> "계속 된다"를 보장하지 않는다. 실제로 3/3 통과 확인 후 배포한 수정이 프로덕션에서
> 다시 틀린 적이 있다 — 반복 측정만이 답이다.

```bash
python -m tests.run_eval               # 전체 1회
python -m tests.run_eval --repeat 5    # 확률적 실패 탐지 (릴리스 판단용)
python -m tests.run_eval --id next-expense-period
```

- **채점 항목**: 답변 내용(포함/금지 정규식) + **어떤 도구를 호출했는지**(라우팅) +
  날짜 고정(today). 문항마다 note에 "왜 이 문항이 생겼는지"(교정 사례)를 기록.
- **운영 규칙**: 오답을 교정할 때마다 그 사례를 문항으로 추가한다. 현재 17문항 —
  규정 수치·차수 일정·시간 상대·위치 찾기·내용 요약·라우팅 구분·쓰기 거절.
- 채점 기준 자체도 다듬었다: 위치 질문("어디 있어?")에 내용 요약까지 요구하면 과채점 →
  정답 페이지 **URL id**로 식별만 검증. 내용 질문("가져와줘")은 핵심 키워드까지 검증.
- 실전 성과: "다음 신청일" 3중 실패(이미지 누락→라우팅 이탈→날짜 비교 오류),
  복합 질문에서 항목 누락(4회 중 1회), 출처 링크 오인용 — 전부 이 체계로 잡고 고정했다.

## 3. 조회 전용 가드레일 (3중)

> 쓰기 기능이 없는 현 단계에서 최악의 실패 모드는 "모델이 쓴 척하는 것"이다.

1. **코드 레벨(진짜 강제력)**: `NotionClient._request`가 GET/조회용 POST 외 전부 차단.
   토큰에 쓰기 권한이 있어도 이 코드로는 물리적으로 쓸 수 없다.
2. **프롬프트**: 조회 전용 명시. 쓰기 요청엔 불가 안내 + 직접 하는 방법/위치 안내.
   "추가했습니다" 류 거짓 완료 표현 금지.
3. **골든 셋**: "회의록에 추가해줘" 문항 — 거짓 완료 표현이 있으면 실패.

## 4. 웹 UI — Apple 디자인 시스템 + 자주 쓰는 질문

- **디자인 전면 교체**: `web/DESIGN.md`(apple.com 검증 토큰)를 CSS 변수로 —
  #0071e3 필 버튼, #f5f5f7 캔버스, SF Pro 타이포, 플랫 깊이, 18px 카드.
  토큰에 없는 값(호버·포커스)은 로컬 확장으로 주석 표기.
- **자주 쓰는 질문 패널**: 데스크톱 좌측 고정 / 모바일 상단 가로 칩. 클릭 → 입력창 채움,
  `{멘토명}` 자리표시자는 자동 선택되어 바로 교체 입력. **사이드바에 프롬프트를 추가하면
  골든 셋에도 같은 질문을 추가한다** — 팀이 가장 자주 누를 질문의 품질이 항상 검증되게.
- 모바일(iPhone) 헤더 수정: 모델 ID 메타가 공간을 먹어 버튼이 밀리던 문제 → 640px 이하 숨김.

## 5. 인프라·운영

- **환경변수 정리**: import 시점 부수효과 제거 — 모든 env 읽기가 `config.env()` 단일 통로,
  첫 호출 때 `.env`(notionchat/.env로 이동) 1회 로드. 설정값은 사용 시점 함수로.
- **정적 파일 CDN 서빙**: vercel.json에 `handle: filesystem` — `/web/*`가 Python 함수를
  거치지 않고 CDN에서 나간다 (함수 호출 수·콜드 스타트 체감 개선).
- **CI 이슈**: GitHub Actions의 `VERCEL_TOKEN`이 무효화되어 자동 배포 실패 중.
  현재는 로컬 `vercel deploy --prod`로 배포. **→ 할 일: Vercel에서 토큰 재발급 후
  GitHub 시크릿 교체.**
- **비용 관측 3계층**: CloudWatch AWS/Bedrock 지표(총량) / Vercel 로그 `[usage]` 필터
  (질문별) / Cost Explorer(청구 확정치). 실측: 개발 포함 하루 ~$0.7, 캐싱이 입력의 ~99%를
  커버. 실사용 기준 월 $5~10 예상 — **무료 LLM 이원화 등 비용 최적화는 불필요 단계**
  (내부 데이터를 학습 허용 조건으로 외부에 보내는 트레이드까지 고려해 보류 결정).
