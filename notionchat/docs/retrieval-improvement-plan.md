# 검색 품질 개선 계획 (retrieval-improvement-plan)

목표: 질문 의도에 맞는 Notion 문서를 정확히 찾아 근거 있는 답을 만든다.
원칙: **측정 없이 개선 없음** — 모든 변경은 평가셋 점수로 전후를 비교한다.

## 단계 0. 준비물 (사람이 작성 — 이 계획의 선행 조건)

### 0-a. 워크스페이스 구조 지도
작성자가 Notion의 각 파트에 어떤 정보가 담기는지 알고 있으므로, 이를 직접 문서화해
시스템 프롬프트에 넣는다. 자동 크롤링보다 낫다(의도가 담긴 선별, 안정 프리픽스라
프롬프트 캐시에 실려 매 호출 추가 비용 거의 없음).

형식 (예시 — `api/core/prompts.py`에 반영):

```
워크스페이스 구조:
- 인터뷰 (page_id: xxxx): 작가/스튜디오 인터뷰 원문과 요약. 고객 페인포인트는 여기.
- 기획 (page_id: xxxx): 기능별 기획서. 앨범 에디터·보정 요청 구조화 스펙 포함.
- 회의록 (page_id: xxxx): 주간 정기회의. 제목 형식 "N월 정기회의".
- 비용 (database_id: xxxx): 인프라·모델 비용 DB. 속성: 항목/월/금액.
```

작성 요령:
- 파트별로 "무엇을 물으면 여기를 봐야 하는지"가 드러나게 한 줄 설명을 단다.
- page_id/database_id를 포함하면 모델이 검색을 건너뛰고 바로 read_page/query_database로
  진입할 수 있다 (도구 호출 절약 + 정확도 상승).
- 구조가 바뀌면 이 지도도 갱신해야 한다. 크게(전부) 쓰지 말고 자주 묻는 영역 위주로
  10~20줄 이내 유지.

### 0-b. 평가셋 (자주 묻는 질문 + 정답)
`tests/eval_questions.jsonl`, 한 줄에 질문 하나:

```json
{"question": "8월 회의에서 결정된 사항은?", "expect_source": "8월 정기회의", "expect_contains": ["앨범 에디터", "9월"]}
```

- `expect_source`: 근거가 되어야 할 페이지 제목(부분 일치 허용)
- `expect_contains`: 답변에 반드시 들어가야 할 사실 키워드 목록
- 15~30문항. 쉬운 것만 넣지 말고 어려운 유형을 섞는다:
  - 시간 상대 질문 ("지난달 회의", "최근 결정")
  - 동의어/표현 차이 (문서 제목과 다른 단어로 묻기)
  - 두 문서를 조합해야 하는 질문
  - Notion에 없는 내용 (정답: "없다/연결 안 됐을 수 있다"고 답해야 함 —
    `expect_contains` 대신 `expect_no_source: true` 같은 필드로 표시)

**단계 0 완료 기준: 0-a 지도 초안 + 0-b 15문항 이상.** 이 둘이 갖춰지면 1단계로.

## 단계 1. 평가 스크립트 (구현)

- `python -m tests.run_eval` — eval_questions.jsonl을 읽어 `run_turn` 실행,
  출처 적중률 / 사실 포함률 / 평균 도구 호출 수 / 토큰 비용을 표로 출력.
- 이후 모든 단계는 이 점수로 전후 비교. 모델 교체 실험(Haiku ↔ 상위 모델)도 이걸로.

## 단계 2. 즉효 수정 (구현, 반나절)

- **날짜 주입**: 시스템 프롬프트는 캐시 보호로 날짜 제외 → 모델이 오늘을 모름.
  `run_turn`에서 질문 앞에 `[오늘: YYYY-MM-DD]`를 붙인다 (캐시 프리픽스 비오염).
- **검색 결과 컨텍스트 보강**: `_search` 반환에 parent(상위 페이지) 정보 추가,
  `page_size`·최신순 정렬을 도구 스키마에 노출.
- **구조 지도 반영**: 0-a를 SYSTEM_PROMPT에 삽입.

## 단계 3. 탐색 전략 프롬프트 (구현)

- 검색 2회 실패 시 구조 지도의 상위 페이지에서 `list_children`으로 내려가는 경로 명시.
- 후보 복수일 때 제목으로 단정하지 말고 상위 1~2개를 read_page로 확인 후 답하기.
- 평가셋으로 MAX_TOOL_CALLS(현 8회) 도달 빈도 확인 후 상한 조정.

## 단계 4. (측정 결과에 따라) 확장

- 평가에서 "키워드 검색 미스"가 주 실패 원인으로 확인될 때만:
  pgvector 사전 적재 + 시맨틱 검색 도구 추가 검토.
  현 계획(docs/notion-chatbot-plan.md)의 "사전 적재 없음" 원칙을 뒤집는 결정이므로
  평가 근거 필수. 작은 워크스페이스에선 단계 2~3으로 충분할 가능성이 높다.
